# /pr-create reference: tiers and the local quality loop

The detail behind Steps 1 and 2 of [SKILL.md](../SKILL.md). Read it when the step needs it: a tier call you are unsure of, a pre-push suite, a review that changed logic, a UI check.

## Why the budget looks the way it does

A ship is measured from the user's word to the merge: about 20 minutes for a Standard change, of which CI is 7, and one CI run. Measured over 40 ships of one iOS + web project (2026-10-01 to 10-03) the median was over an hour and 20-56M input tokens, with CI itself never the slow part. The hour went to four reviewers and a second review on nearly every PR, the same suites run locally and then in CI, a 25-minute suite repeated after a review fix, branches re-merged with main because it had moved, and a red main found only when the PR's checks failed. Each rule below that says "once", "only when" or "not a reason" is there for one of those.

**Division of labor.** CI owns the deterministic suites; the shipper owns judgment. Stacks with any `ci` value in `.claude/test-manifest.json` (`"pr"` runs on the PR's checks, `"nightly"` on the schedule) are never re-run locally. A suite CI runs on the PR is not also run in full here, `tier: "fast"` or not: on one iOS + web project the 4-minute backend suite ran two or three times per ship before CI ran it again, and a suite that drives a browser flaked on the loaded Mac, which cost a further full run each time. A project with no `ci` fields has no CI: then the local test run covers every stack. One exception, the manifest's `ci.prePush`: a suite whose only CI home is one self-hosted machine runs here instead, on the shipper's machine, and its pass is attested to CI. A suite that queued every open PR behind every other on a single runner costs no queue at all when each ship runs its own.

## Is main green? (Step 1)

`gh run list --branch <default> --limit 12 --json databaseId,workflowName,conclusion,status,event,createdAt` (skip when the repo has no CI). Take the newest completed run of each workflow that gates PRs or runs nightly. One of them red, or an open "red on main" issue (`gh issue list --search "red on main in:title" --state open`), means this PR's checks will likely fail for a reason that is not its own: read the failure now (`gh run view <databaseId> --log-failed | grep -E -m 20 'FAIL|Error|failed|✘|error:'`; the log's tail is only job cleanup). If this diff does not fix it, say so in your first status line, carry on, and name it in the report: when the ship script later sends back that check as red, it is known-red, not this PR's. Three ships of one project each found the same red nightly e2e test only after their own 7-minute CI run, and stalled 20-30 minutes apiece.

## Tiers (Step 1)

Size alone never makes a change Deep: a long diff gets a reviewer per area (Step 2), not more rounds. When every PR over ~300 lines was "Full", nearly every PR was, and each paid for six review agents and 15-40 minutes before its PR opened. A `ci.prePush` suite runs in every tier whenever the diff matches its `when`: it replaces the CI run, so a Simple change that touches its paths still runs it.

**Who else is landing.** `rollcall queue status` from the worktree reads local state (no network): the train landing now, the PRs waiting, the PRs whose checks rollcall watches, each marked when it touches this branch's files (`<- touches your files: ...`). Name those PRs in the tier line, since this ship may get a conflict back later. Nothing waits on them: every gate runs now, on this branch as it is. Don't merge another branch or main in ahead of time and don't wait for another ship: when this PR's turn comes and it is still green and merges cleanly, the lander lands it as it is.

## Pre-push suites (Step 2, first)

For each manifest `ci.prePush` entry whose `when` globs match a changed file, start its `ship` command now (its `command` when it has no `ship`) as a background Bash call (`run_in_background: true`, `timeout` 3600000) and go on: it runs beside the review, not after it. `ship` runs only the suites the diff names directly. A green PR lands as it is, so this may be all that runs before it lands; the rest runs on the merge queue's train with `command` (when the PR goes through one, or the project sets `land.retest`) or after the merge, in the default branch's full run where the project has one. When the entry has `notes`, they say how to scope the command to this diff (which suites to name in a placeholder such as `<suites>`): fill it in from the diff, and name what ran in the report. It is a script, not an agent: one command, one wake-up. Collect it before Step 4's push. A failure is a test failure like any other (fix, then run the command again). A test it reports as flaky (failed, then passed on the suite's own retry) is named in the report, never re-run for. If a later step changed a file matching `when` after the run started (a reviewer's fix), run the command again on the final code and wait for it; Step 4's `attest` refuses code that did not pass. No entry matches: nothing starts and nothing is attested.

## Quick checks

What catches an obvious failure in about a minute, run directly (no agent): the compile / type-check / build-free checks (`tsc --noEmit`, a migration or lint script), plus the tests for what changed - the test files this diff edits and the ones covering the modules it touches (`pytest tests/test_x.py tests/area/`, the runner's equivalent). A `tier: "fast"` stack with no `ci` field has no other home and runs in full. A fast stack CI runs on the PR does not: CI runs all of it once, on the commit that matters.

## Review (Standard/Deep): one pass

First commit the change as it stands (a local commit, nothing pushed): the reviewer's fixes are then the working-tree `git diff` (with the docs agent's edits beside them: files under docs/, and README.md when it is due), which is what a second reader needs and what the report counts. Spawn **code-reviewer** with the change summary + file list (and, for a task's worktree, the owner's words from the brief, verbatim and labelled as the acceptance criteria), in the same message as the docs agent (Step 3) so they run side by side; it fixes issues directly, and its brief covers cleanup (reuse, dead code, needless complexity) as well as bugs, so no separate cleanup pass follows. A diff that spans areas a single reader would skim (backend and iOS, say, past ~600 hand-written lines) gets one reviewer per area in that same message, never a second round. Then:

- Its fixes were small or mechanical (its report says "Logic changed by fixes: no"): done. Re-run the quick checks for the files it touched.
- Its fixes changed logic: spawn **code-reviewer** once more on that delta only (`git diff` of what it changed, minus the docs agent's files (docs/ and README.md), not the whole PR), then the quick checks. That is the only second review Standard gets.
- **Deep** adds one more **code-reviewer**, in that same first message, reading only the risky part (the migration, the auth or payment path) with the question that makes it risky spelled out ("can this lose or expose a user's data?"). Tell it to report findings and not edit, since the first reviewer is editing the same files; you fix what it finds, then run the quick checks. Two independent reads of the dangerous code, not more rounds on the rest. No `/simplify` here: the reviewer's cleanup step covers it, and in a timed run four cleanup agents on top returned mostly what the reviewer already had.
- The docs agent runs beside the review, so a review fix that changes behavior can leave a doc it just wrote stale: correct that sentence yourself after the fix (before Step 3's final gate run), no second docs pass.

## Local-only stacks (Standard/Deep)

CI-owned means any `ci` value: `"pr"` stacks run on this PR's checks, `"nightly"` stacks on the schedule, and neither is re-run locally (the one exception, a suite named by `ci.prePush`, is started at the top of Step 2 and is not an agent's job; a persona suite run locally at ship cost 20+ minutes and up to 30M tokens per iOS PR, for coverage the nightly already gives). Only `tier: "full"` stacks with no `ci` field that the diff touches run here: spawn **test-runner** in **local tier** (tell it so explicitly) with the change summary; it runs just those and validates the feature itself (curl new routes, schema consistency). Nothing left: skip the agent and say why. When the diff touches what a nightly suite covers (the stack's manifest `notes` or the project's ship skill say which flows), dispatch just those suites on CI - the manifest's `ci.notes` give the command (e.g. `gh workflow run ios.yml --ref <branch> -f suites="<Suite>"`) - and name the run in the report; `gh run watch <id> --exit-status` as a background call when the ship should not end before it. No `ci` fields anywhere in the manifest: the project has no CI and local tier is every stack.

## UI verification: a judgment call, not a rule

CI's e2e suites (when the project has them) cover existing golden paths on every PR. Run `/frontend-test {summary}` (web) or `/ios-sim {summary}` (iOS: the ios-driver agent taps through the changed flows in the simulator and returns screenshots; a project's ship skill may say what else its visual check needs) when the change warrants eyes on it: a new screen or route, an explicitly visual change (layout, theming, spacing, motion), or a change to a shared surface many screens render (shell, nav, design tokens, a core component) - then scale its breadth to the risk, up to every affected route. Skip it for UI-adjacent changes CI already exercises (copy, a prop threaded through, a fixed handler with e2e coverage), and say why in the report. PASS: proceed; WARN: ask the user; FAIL: treat as a test failure. With no e2e in CI at all, run it for any UI change.

## Failures

Fix (failures classified as test bugs go to `/update-tests` with the diagnosis), re-run what failed - the failed tests themselves (`pytest --lf`, or the runner's equivalent), not the whole suite. Loop until clean. Before the push, the quick checks are green on the final code: one run after the last change, not one per fix. The full run of a CI-owned suite is CI's. Do not proceed with known failures - report them instead.

## Graduation nudge

If the local test run in Step 2 took more than ~10 minutes of wall time (test-runner reports it), or the project has no CI and two or more `tier: "full"` stacks, end the report with one line: "Local ship tests took ~N min: `/ci-setup` would move <stacks> into CI." Say it once per project per session; never run `/ci-setup` without the user's word.

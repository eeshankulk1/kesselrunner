# rollcall

Awareness for parallel AI coding-agent sessions on one machine (Claude Code, Codex).

When several agent sessions work on the same repo, a person usually ends up relaying facts between them: "another agent is in this repo, use a worktree", "main moved, merge it", "the other agent is doing part A", "part A is done". rollcall works these facts out from harness hooks and git, and tells each session only the ones that concern it. Agents declare only their intent (a claim). Everything else is derived automatically.

- **Main checkout, read-only.** Agents edit in task worktrees, never in a repo's main checkout: an edit there is denied with the `git worktree add` command for a task worktree. A repo opts out with `rollcall allow-main`.
- **Shared checkout, blocked.** When a second live session tries to edit a checkout another session is working in, the edit is denied, and so are git commands that would change that checkout (`checkout`, `reset`, `stash`, `commit`, `pull`...). The message includes the exact `git worktree add` command to run instead. On Claude Code the deny holds in every permission mode, including bypass permissions.
- **Live temp folders, kept.** A Bash command that can delete another running session's Claude temp folder (`/tmp/claude-<uid>/<project>/<session-id>`: its scratchpad and background task output) is denied, with the list of those folders; a session's own folder and those of ended sessions delete freely. A target the command does not spell out (a loop variable, `xargs rm`, a glob above a session's folder) counts as the whole temp root.
- **File overlap, warned.** Editing a file that another session (in any worktree) has edited or claimed gets a one-line warning with that session's intent.
- **Main moved.** When `origin/main` gains commits that collide with this session's work (it no longer merges into the branch, or it changed a file the session has uncommitted edits in), the session gets one notice. Committed work that still merges cleanly hears nothing.
- **Merge queue.** A session ships by joining the queue once its PR is open, pushed and green (`rollcall queue add`). The lander, a script and never an agent, lands ready PRs in the order they became ready, landing a PR whose own checks are green and that merges cleanly as it is, within seconds (main's own checks after the merge catch what two PRs break together). The rest (a failed check, a conflict, a `land.serial` clash, branch protection that wants an up-to-date branch, or `land.retest` in the manifest) go in trains of up to 4, tested once as one tree and merged as that tree. Each session hears only its own news: landed, a conflict to resolve, a check that failed and why it is this PR's, or parked for the owner. No session waits on another while it builds, and none merges main ahead of time.
- **Results keyed by inputs.** `rollcall results` records that a check passed for a set of input files (the test manifest's `inputs` globs), as a ref on origin. Any later tree with the same inputs - after a merge of main that touched other files, a docs amend, another machine, CI - finds the pass and skips the check.
- **Merged worktrees, collected.** `rollcall gc` removes agent worktrees whose work landed (merged, squash merges included; clean; no session or process inside), running the project's teardown first. It runs in the background at session start and end, and once a day per repo it also deletes the merge queue's leftover refs (see Worktree gc). A worktree an open task names (a merged task stays open while its worker runs its after-merge steps), or a branch made in the last day with nothing committed yet, is kept.
- **Tasks and supervisors.** A task is work that outlives any one session: the owner's words verbatim, notes, its worker sessions, state, PR and last report. A session can be a named supervisor (`rollcall supervise falcon`, or `falcon` in a terminal tab), one live session per name, each with its own tasks and ids: it starts a worker per task (an interactive session in tmux, on Claude Code or Codex), edits no project files itself, and its workers report through the task record. One watcher process per supervisor home takes the steps that need no judgment itself, tells the owner the plain facts on the status line, and types the rest into the supervisor. A supervisor sent to the background keeps its name and tasks.
- **Claims, messages, done, wait.** Sessions say what they are doing, message each other, and wait for each other. `rollcall wait` runs in the background, and when it exits the harness wakes the idle session.

No daemon, no server, no LLM calls, zero dependencies. The hook hot path does local file I/O only.

rollcall ships inside [kesselrunner](../../README.md), which installs it and wires up its hooks. There, the commands a person types are in [docs/commands.md](../../docs/commands.md#rollcall), and the reasons behind worktrees and the merge queue in [docs/principles.md](../../docs/principles.md).

## Install

```bash
npm install -g rollcall
```

Needs Node 20+ and git 2.29+. Supervisor mode also needs tmux. macOS and Linux.

### Claude Code

Add to `~/.claude/settings.json`:

```json
{
  "hooks": {
    "SessionStart":     [{ "hooks": [{ "type": "command", "command": "rollcall hook session-start", "timeout": 10 }] }],
    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "rollcall hook prompt-submit", "timeout": 10 }] }],
    "PreToolUse":  [{ "matcher": "Edit|Write|MultiEdit|NotebookEdit|Bash", "hooks": [{ "type": "command", "command": "rollcall hook pre-tool-use", "timeout": 10 }] }],
    "PostToolUse": [{ "matcher": "Edit|Write|MultiEdit|NotebookEdit|Bash", "hooks": [{ "type": "command", "command": "rollcall hook post-tool-use", "timeout": 10 }] }],
    "Stop":       [{ "hooks": [{ "type": "command", "command": "rollcall hook stop", "timeout": 10 }] }],
    "StopFailure": [{ "hooks": [{ "type": "command", "command": "rollcall hook stop-failure", "timeout": 10 }] }],
    "SessionEnd": [{ "hooks": [{ "type": "command", "command": "rollcall hook session-end", "timeout": 10 }] }]
  }
}
```

It also helps to tell your agents what the notices mean and when to claim. The [agent instructions](#agent-instructions) below are a ready-made block for `CLAUDE.md` / `AGENTS.md`.

### Codex

The same entries go in `~/.codex/hooks.json`, which uses the same schema. Codex's docs (0.146) list the same events and payloads, with its shell tool as `Bash` and its `apply_patch` edits as `Edit`/`Write`, so the matchers above cover them; it has no StopFailure and sends no `agent_id`. Codex runs a hook only once it is trusted (`/hooks`), and pins each by hash. Where a Codex version fires no edit hooks, rollcall falls back to session-start awareness, prompt-time notices, and the CLI.

A supervisor's workers can run on Codex too (see Harnesses, below); the supervisor itself runs on Claude Code.

## What a session sees

Notices are injected as context, one fact per line, each prefixed `[rollcall]`. When nothing relevant changed, nothing is injected.

```
[rollcall] 3f9a1c2e (main, main checkout) is also in myapp, active 2m ago: claimed "fix the login bug" [src/auth/**]
[rollcall] 3f9a1c2e is already working in this checkout, so your edits here will be blocked. Create a worktree before editing: git -C "/code/myapp" worktree add "/code/myapp/.claude/worktrees/6f2e1a0b" -b wip/6f2e1a0b origin/main
```

A denied edit returns the reason to the agent (a denied git command reads the same, starting `` `git checkout` blocked: ``):

```
[rollcall] Edit blocked: session 3f9a1c2e (main, main checkout) is already working in this checkout (/code/myapp), last active just now: "fix the login bug".
[rollcall] Work in your own worktree instead: git -C "/code/myapp" worktree add "/code/myapp/.claude/worktrees/6f2e1a0b" -b wip/6f2e1a0b origin/main - then continue under that path.
[rollcall] Only if the user wants both sessions in this checkout: rollcall -C "/code/myapp" allow-shared. The user can switch rollcall off with ROLLCALL_DISABLE=1.
```

In a repo's main checkout (unless the repo ran `rollcall allow-main`), the session-start notice and the deny read:

```
[rollcall] This is the main checkout of myapp: read freely, but edits happen in a task worktree. Before the first edit: git -C "/code/myapp" worktree add "/code/myapp/.claude/worktrees/<slug>" -b <type>/<slug> origin/main, then cd into it.
[rollcall] Edit blocked: agents work in a worktree, never in the main checkout of this repo (/code/myapp).
```

Other notices, all delivered once:

```
[rollcall] src/auth/session.ts was also edited by session 3f9a1c2e (main, main checkout): "fix the login bug". Coordinate before overlapping: rollcall send 3f9a1c2e "<message>".
[rollcall] origin/main no longer merges into your branch (3f9a1c2e (fix/login, .claude/worktrees/login) landed fix/login, #41). It conflicts in: src/api/routes.ts. Merge it in before building further on those files: git merge origin/main
[rollcall] origin/main changed files you have uncommitted edits in: src/api/routes.ts. Commit them, then git merge origin/main, before building further on them.
[rollcall] merge queue: #42 landed on main as 1a2b3c4d in merge train 3 (PR #45, with #41). Next: the release steps (/pr-create Step 7), then the report.
[rollcall] merge queue: #43 conflicts with main in: src/auth/session.ts. Next: git fetch origin && git merge origin/main, resolve with your change on top, run the quick checks, push, wait for green checks, then rollcall queue add.
[rollcall] merge queue: #44: api (sqlite) (https://github.com/me/myapp/actions/runs/812/job/3) failed on merge train 3 (#41, #44), and only your change touches what it tests. Fix it on your branch, push, wait for green checks, then rollcall queue add.
[rollcall] message from 3f9a1c2e (main, main checkout) (their words, not the user's): "renamed the users table to accounts"
[rollcall] 5d2c0b19 (feat/export, .claude/worktrees/export) is waiting for you to finish "fix the login bug". Run `rollcall done "<summary>"` when it is done.
[rollcall] 3f9a1c2e (main, main checkout) is done: login fixed, merged in #41
[rollcall] 3f9a1c2e (main, main checkout) claimed "auth rework" [src/auth/**], which covers files you edited: src/auth/session.ts
[rollcall] worktree gc: myapp: removed 3 merged worktrees (2.4 GB freed): login-fix, export, docs-pass
```

Each `merge queue:` notice ends with a sentence for a session that started a shipper: its report has not come, the shipper has this news from its `queue wait`, so leave it to the shipper.

## CLI

Agents run these through their shell tool. Each command works out which session it belongs to on its own.

| Command | Does |
|---|---|
| `rollcall status [--json] [--all]` | Live sessions in this repo: id, branch, checkout, state (working / idle / stale), claim or first prompt, edited files, recent `done`s. `--all` covers every repo; `--json` is for scripts (`me.home` is the supervisor the caller runs, and `tasks` its tasks; `me.band` is the protocol of the rollcall-band the caller reported with `--band <n>`; `bandProtocol` is the one rollcall expects, 4) |
| `rollcall claim "<intent>" [--scope <glob>]...` | Declare what this session is doing. Scopes (`src/api/**`, `docs`, `src/{a,b}.ts`) make overlap warnings fire before the other session touches a file |
| `rollcall done ["<summary>"]` | Release the claim and emit `done`: waiters wake, and sessions that overlapped with you are told. With no summary, rollcall writes one from the first prompt, branch and edited files |
| `rollcall send <session\|all> "<msg>"` | Message a session (id prefix, or any unique part of its claim or prompt) or every session in the repo. It arrives with the session's next tool call or prompt |
| `rollcall wait <session\|claim> [--timeout <min>]` | Block until that session runs `done` or ends. Also returns early if a message arrives for you. Exit codes: 0 done/message, 2 the session died without `done`, 124 timeout |
| `rollcall queue add [--owner-ok "<their words>"]` | Join the merge queue with this branch's PR. Refuses, with the fix (exit 1): the default branch, uncommitted work, HEAD not pushed, no open PR, a draft, a PR that targets another branch, checks pending or red, and a PR that carries another open PR's unlanded commits while that PR is not in the queue ahead of it. A PR the lander sent back is checked by the guard first: a hit parks it (exit 2). Prints its place, sets its task (when the worktree is a task's) to `queued` with the PR's link, and starts the lander when none runs. It also refuses a PR with open review threads (see Review loop); `--owner-ok` says the owner told you to land it as it is, recorded as a task note and covering exactly the threads open then |
| `rollcall queue wait [--timeout <min>]` | Block until this branch's entry has news, then print it with the next step: `landed`, `conflict`, `failed`, `left` or `parked`. Also returns on a message for you. Run it in the background; it also restarts a lander that died with entries waiting. Exit codes: 0 news/message, 3 your own session ended, 124 timeout |
| `rollcall queue status [--json]` | The train landing now and its stage (while a pre-push suite runs: its time so far against its usual time, the median of its last 5 passes in the lander, and its log's last line), the entries waiting in order with the files each changes (marked where they touch this branch's), the parked ones and why, and the last outcomes (each landing with how long after it first joined, and after the owner said "ship it" on its task). Beside a running suite it names what else runs tests on this machine: Actions runner jobs and the repo's pre-push commands that sessions started (one `ps`). Outside a checkout it shows every repo with a queue; `rollcall -C <dir> queue status` shows that repo's (`queue status -C <dir>` is refused, as is any unknown argument) |
| `rollcall queue leave ["<why>"]` | Leave the queue without landing. A train it was in forms again without it |
| `rollcall land` | Gone: prints where to go instead (`rollcall queue`) and exits 1. Kept for one release |
| `rollcall results key\|check\|record <name> [--rev <commit>] [--json]` | Input-keyed results for a test-manifest stack or `ci.prePush` entry. `key`: the hash of the files its `inputs` globs name at a commit (default HEAD; inputs default to the whole repo, or the entry's `when`). `check`: exit 0 when that key already passed (a local ref or origin's `refs/passed/<name>/<hash>`, which gc deletes after 7 days: see Ref sweep), 1 when not; `--github-output` writes `passed`, `key` and `commit` for a workflow step and exits 0 either way. `record`: the pass, as that ref, here and on origin (exit 3 when the inputs have uncommitted changes; 1 when origin refused it, kept locally). Exit 2 is a usage error, such as a name the manifest lacks. `src/results.mjs` runs on its own too (`node results.mjs check api`), which is how CI uses it |
| `rollcall results run <name> [-- <command>]` | `check`, and when the key has not passed: run the command (default: the stack's `testCommand` in its `dir`, or the entry's `command`) on HEAD, then `record`. Records nothing when the command fails (its exit code) or the inputs changed while it ran (exit 3) |
| `rollcall allow-shared [--off]` | Let this session edit a checkout another session is using (on purpose) |
| `rollcall allow-main [--off]` | Let agents edit this repo's main checkout (sets `git config rollcall.mainEdits allow`, shared by every worktree), as a shared workspace: the shared-checkout block doesn't apply there either; `--off` restores worktrees-only |
| `rollcall gc [--dry-run] [--all]` | Remove merged, clean, unused worktrees under `.claude/worktrees/` and their branches, running the test manifest's `worktree.teardown` first; lists what it kept and why, and how many old refs it deleted; it also sweeps what ended work left on the machine (see Leftovers). `--all` covers every repo rollcall has seen |
| `rollcall clean [--yes]` | The delete list for a low disk: folders that are only rebuildable, with sizes (see Leftovers). Deletes nothing until `--yes`, which takes what the list showed in the last day; on a list not shown yet, `--yes` prints it and deletes nothing |
| `rollcall remind "<text>" --in <30m\|2h\|1d>` | A line for the owner later, for a step only they can take: under their prompt and a notification, with no model turn. It keeps the home's watcher running until it is due. Bare: what is set |
| `rollcall away [on \| off \| status]` | Away mode, for the whole Mac (see Away mode): while it is on, a task worker's permission prompt is held and its question waits on its task, so it carries on without the owner. `off` lists what got done and what was held. The owner's own: refused inside a worker |
| `rollcall away allow\|deny <id> ["<why>"]`, `rollcall away allow-all` | Answer what away mode held, from the owner's own terminal or `!` in the Falcon (refused inside a worker; the Bash guard stops an agent's own shell): the worker hears it as its next prompt, and an approved request goes through once |
| `rollcall blockers [clear <kind>]` | What stops work on this Mac or account now: `usage`, `usage-codex` (Codex's own limit, which holds only tasks running on Codex), `billing`, `disk`, `power`, `memory` (see Machine trouble). `clear`: it is fixed, so what waits on it goes on |
| `rollcall park [--dry-run]` | Stop the sessions nothing needs, to free memory (see Parking): each worker due to park, and each falcon supervisor whose conversation has been quiet an hour between turns (`ROLLCALL_PARK_SUPERVISOR_MS`) with no terminal on it used since, whatever its tasks; says what it parked. It also restarts the watcher of a parked supervisor with open tasks when that one is gone. A home's watcher parks on time; a sweep also runs this in the background at most every 10 minutes (`ROLLCALL_PARK_MINUTES`) from SessionStart; `ROLLCALL_PARK=0` turns parking off |
| `rollcall supervise [<name>] [--off]` | Make this session supervisor `<name>` (with none: the session's own name, else the next free one): it takes the name's lock (refused while another live session holds it; that session stays a plain one), its edit tools are denied inside any git checkout, its home's watcher hands it its tasks' news and its status line draws their chips (inside the Falcon, the tab bar does). It stamps `skills/supervisor/SKILL.md`, and the supervisor hears once at prompt submit when that file changed since it loaded. `--off` lets go of the name |
| `rollcall task new "<title>" [--repo <dir>] [--words "<text>" \| --words-file <f>] [--type <t>] [--slug <s>] [--base <ref\|task>] [--after <id>]... [--until landed] [--ship] [--note "<text>"]... [--kind build\|discuss] [--no-worktree \| --no-repo \| --worktree <dir>] [--browser] [--model <m>] [--effort <e>] [--issue <n\|url> \| --pr <n\|url> \| --branch <name>]` | Record a task in this supervisor's home (`t1`, `t2`... from the home's own counter, never reused) and create its worktree at `.claude/worktrees/<slug>` on `<type>/<slug>` from origin's default branch (or `--base`: a git ref, or a task, which stands for its branch and need not have pushed yet), noting the commit it starts from. A base that does not resolve stops it before anything is written. The record exists before the worktree, so gc never meets one without the other. `--worktree` takes over a worktree that exists (the owner's "continue there"), on its branch, noting where that branch left the default branch; refused for the main checkout, a detached HEAD, the default branch, or another open task's worktree. `--until landed` (with `--after`) holds the task until those tasks have landed, not just opened a PR, and its first prompt tells the worker to merge origin's default branch in first (the plan-then-build pair: a plan task's worker starts the build task this way). `--ship` records that the owner already said to ship it: its worker runs `/pr-create` with no ship question unless the change is something the owner sees or the diff goes beyond what they asked. `--no-repo` makes a job on the machine (a disk cleanup): a plain folder under `_machine/jobs/`, no repo, no worktree, no PR, finished with `--state closed`; it takes no `--repo`, `--worktree`, `--no-worktree` or `--base`. `--harness claude\|codex` names the agent CLI its workers run on, else `ROLLCALL_WORKER_HARNESS`, else `claude` (see Harnesses). `--model` (an alias or id; on Codex a Codex model id) and `--effort` (`low` to `max`) go on the record: its workers run on them instead of the harness's (see Workers in tmux) `[title]` may be left out with `--issue`. `--issue` takes the issue's title (if none given), url and body as the first words (via "issue"), records `t.from`, and tells the worker its PR body says `Closes #N`. `--pr` carries on an open PR of the same repo: its head branch is checked out as it is, `t.pr` is set, the worker pushes to it and opens no new PR (forks are refused). `--branch` checks out an existing local or origin branch as it is. These three take no `--worktree`, `--no-worktree` or `--no-repo`; `--pr` and `--branch` take no `--base`. Besides the worktree, `task new` hands out a block of ports when the manifest uses `{port}`, and starts in the background a copy of the gitignored files `.worktreeinclude` names from the main checkout, then the manifest's `worktree.setup` (see Runtime). A discussion task gets the copy only; a worktree taken over with `--worktree` gets nothing new. |
| `rollcall task list [--all] [--json]` | First a `usage:` line (see Usage meter) when a reading is fresh, then this supervisor's open tasks (and those finished in the last hour): state, open question, worker (working, idle, waiting on a prompt in its window and what it asks, stopped, a v2 worker; "on Codex" for a Codex one), its context use in percent and tokens, PR, its unread messages; for an idle worker, what it left running (Claude Code's `background_tasks` at its last Stop) and its last words, and for a finished task's, when its window closes; then the decisions waiting on the owner. A plain shell lists every home's, prefixed with the home. `--json` also carries each task's `harness` and the meter as `usage` |
| `rollcall task show <id\|here> [--json]` | One task whole: the owner's words, notes, worker sessions, last report. `here` is the worker's own task (its environment names it), else the task whose worktree holds the current folder With `--json`, `task show` and `task list` carry `runtime: { ports, setup, actions, previews, spotlit, archived }` and `from`. |
| `rollcall task setup <id\|here> [--rerun] [--wait]` | A task's worktree setup: how it went, or run it again (same as `rollcall setup` run in its worktree) |
| `rollcall task run <id\|here> [list \| start\|stop\|restart <name\|all> \| log <name>]` | A task's run actions (same as `rollcall run` in its worktree) |
| `rollcall task archive <id> [--yes]` | Free a task's worktree and ports without losing work. Without `--yes`: prints what goes (folder, size freed, uncommitted files, run actions, ports) and changes nothing. With it: stops the worker and run actions, saves uncommitted work (untracked too, not gitignored) to `refs/rollcall/archive/<home>/<id>` (never pushed), runs teardown, removes the worktree and frees the ports. The record and the worker's conversation stay. Refused from a worker |
| `rollcall task restore <id>` | Add the worktree back at its old path on its branch, apply the saved work as uncommitted changes (staged comes back unstaged), say if origin's branch moved (it never rebases), drop the ref, rerun setup, resume the worker. Refused from a worker |
| `rollcall task spotlight <id> [--off [--force] \| --sync]` | Run a task's files from the main checkout, for what can only run from one place. One task per repo. Refused while the main checkout has tracked changes of its own and from a worker. Moves the main checkout, detached, to a snapshot commit of the task's files (tracked changes and untracked files, not gitignored); the supervisor's watcher keeps it in step every poll (`--sync` does it now). `--off` returns the main checkout to its branch or commit with its files byte-identical (`--force` when it differs). gc ends a spotlight before removing the worktree |
| `rollcall ports [--json]` | This checkout's block of ports, handed out on first ask. The main checkout uses the manifest's `ports.default` when set |
| `rollcall manifest [--json]` | The test manifest with this checkout's ports filled in for `{port}` and `{port+N}` |
| `rollcall setup [--rerun] [--wait] [--json]` | How this worktree's setup went; `--rerun` runs it again in the background, `--wait` waits for one that runs (the worker's launch script uses it) |
| `rollcall run [list] \| start\|stop\|restart <name\|all> \| log <name> [--lines <n>]` | This checkout's run actions: the manifest's `run`, else `dev` (`devServer.command`) and `backend` (`backend.startCommand`). Each starts as its own process group with a log under `_runtime/<key>/actions/`, survives a parked worker, and stops on archive and gc. A running action's `url` shows in `task show` and as `runtime.previews` in its JSON |
| `rollcall serving <port\|url> [--json]` | Which checkout serves a port. Exit 0: this checkout. 1: another (it names the task). 2: nothing listens. A browser or live-API check trusts a result only after exit 0 |
| `rollcall task set <id\|here> [--state ...] [--question "<q>"] [--ask-json <file\|->] [--pr <url>] [--title "<t>"] [--kind build\|discuss]` | A worker's report. States: `working`, `needs-you`, `pr-open`, `queued`, `landed`, `closed`; a state change clears the open question, and `needs-you` is refused without one. `--ask-json` (AskUserQuestion's own `questions` array) makes it a picker question, with `--state needs-you`. `needs-you`, `pr-open`, `landed` and `closed` from anyone but the supervisor queue a wake for it. A worker's change to a finished task is refused, but for `pr-open`, and the supervisor's is not. A worker's `landed` or `closed` is refused until it saved a report in its current session (`task output`), and `closed` (anyone's) while `gh` shows an open PR on the task's branch. `--kind` turns a discussion into a build or back; set by anyone but the worker, it leaves the worker a message that its contract changed and how to print its brief as it now stands |
| `rollcall task words <id\|here> "<text>"` / `note` / `output [--file <f>]` / `close ["<why>"]` | Add the owner's words (verbatim; `-` reads stdin; they close the task's open question), a note (a decision; with `--home <name>`, a supervisor's note into another's task, which its worker hears, and the only write across homes; a worker's `grew: ...` and `reply: ...` notes, and the older `handoff: ...` one, wake the supervisor), the worker's report (the next wake that carries news of a question or a finish carries it too, once); finish a task that lands nothing (the same refusals as `set --state closed`) |
| `rollcall task stage <id\|here> "<stage>" \| done` | The ship's stage now, which the shipper notes step by step: the task's tab shows it with its minutes against the usual time (the middle of its last runs in that repo, `<repo-key>/stages.json`), plus "Mac load high" when load passes 2 per core, and a stage past twice its usual is one line for the owner, once. A queued PR's tab shows the lander's suite against that suite's usual time instead. Outside a task `here` does nothing |
| `rollcall task handoff <id\|here> ["<text>" \| --file <f>]` | A worker's handoff: the prompt the owner would paste into a fresh session to carry on (where the work stands, what is done, the files to read first and what each is for, what remains, the owner's decisions, open questions). Kept on the task for the next worker's brief; it wakes the supervisor to start that worker (`start.mjs --fresh`) and lowers the cap flag. A supervisor cannot write one |
| `rollcall task wait-for <id\|here> <disk\|power\|billing\|"<check>"> [--every <minutes>] [--why "<text>"]` | A worker's wait, moved out of its context (see Waits): it ends its turn and parks, and rollcall brings it back when the blocker closes or the check exits 0 |
| `rollcall task tell <id> "<text>" \| -` | The supervisor's message to a worker: a file in its inbox, and a fixed doorbell line typed into its window (later, while a dialog is open there or it is not running; the reply says which, and how to resume a worker that stopped) |

### Waiting without polling

In Claude Code, run the wait as a background Bash command and end the turn:

```
rollcall wait 3f9a1c2e      # Bash, run_in_background: true
```

The idle session wakes when the command exits, and the command's output (`... is done: <summary>`) tells it why.

### Landing through the queue

Two sessions told to ship within minutes of each other. Each runs its own gates at once, on its own branch, and joins once its PR is green:

```
$ rollcall queue add                 # session A, on fix/login (PR #41)
[rollcall] queue: #41 (fix/login) joined: place 1 of 1.
[rollcall] queue: now run `rollcall queue wait` in the background; it exits with the next step (landed, a conflict, a failed check, or parked). Push nothing to fix/login meanwhile: a new head takes it out of the queue.

$ rollcall queue add                 # session B, on feat/export (PR #42), two minutes later
[rollcall] queue: #42 (feat/export) joined: place 2 of 2.

$ rollcall queue status              # session A
[rollcall] merge queue for myapp: 2 waiting, train 1 landing; lander running (pid 4242, since 3m ago)
  train 1: #41, #42 - CI on #43 (train started just now)
  1. #41 fix/login, ready 3m ago: src/auth/session.ts
  2. #42 feat/export, ready just now: src/export.ts, src/auth/session.ts  <- touches your files: src/auth/session.ts

$ rollcall queue wait                # A, in the background; exits when the train lands
[rollcall] queue: landed - #41 landed on main as 1a2b3c4d in merge train 1 (PR #43, with #42). Next: the release steps (/pr-create Step 7), then the report.
```

Here the two PRs went in one train (they touched the same file, or the project sets `land.retest`; a green PR that merges cleanly lands alone, at once). The lander merged both heads onto main as one tree, ran the checks once on it (train PR #43), and merged that PR; GitHub marks #41 and #42 merged because their heads are now in main. Had the two conflicted, A would have landed and B would have heard `conflict` with the files.

### Review loop

Three mechanics for feedback that is exact and reaches the worker without a PR.

**Line comments.** `task comment` stores a comment in the home file `comments-<taskid>.json`, under the home lock like the outbox. Each keeps the diff hunk and the lines it was written on, so listing finds a moved line again or marks the comment stale. Pending comments go out with `task comments <id> send` as one `notice` item on the worker's delivery queue, so Claude and Codex workers get them alike. The worker answers each: `resolve` for what it changed, `reply` for an answer; `reply --open` leaves it for the owner and wakes the supervisor. `task show` has a line with the open comments, and `--json` carries `comments`.

**PR review threads.** `rollcall pr threads|reply|resolve` wrap `gh api graphql`. A bot's unresolved thread with the same bot, path and first-comment text as one already resolved or answered counts as answered, so a bot that repeats itself on each push does not reopen the loop. `queue add` refuses a PR with open threads unless `--owner-ok "<their words>"` is given; that is recorded as a task note and covers exactly the threads open at that moment. The lander checks threads in its settle loop (a clear answer holds for a minute, `ROLLCALL_QUEUE_THREADS_MS`, so idle rounds every few seconds do not spend GitHub's GraphQL budget) and again, always fresh, right before the merge; a new thread takes the PR out of the queue with news of kind `review`. Threads it cannot read hold the entry, like any `gh` failure, and before a merge they send the train back to form again rather than land unread. That is not counted as a bounce, and the test-weakening guard does not run for it. Claude Code's `/autofix-pr` runs only as a cloud session and cannot list or resolve threads, hence these wrappers.

**Turn snapshots.** Each linked worktree gets a private bare repo at `<ROLLCALL_HOME>/_snapshots/<sha1 of the path, 16 hex>.git`, whose `objects/info/alternates` points at the repo's objects and whose refs are `refs/turns/<n>`. They sit outside the repo's own refs, so `git push --mirror` carries none. A take runs against the snapshot repo's own index (seeded once from the worktree's and kept between turns, so files that did not change, untracked ones included, are not hashed again) and never touches the branch, HEAD, the real index or the stash; a turn that changed nothing is not written. Takes and restores in one worktree queue on a lock beside the repo (`<hash>.git.lock`, which holds its holder's pid; a dead holder's lock is taken over), and `git gc --auto` packs the repo's loose objects as they pile up. The Stop hook starts the take detached (SessionStart a baseline), only in linked worktrees and never for supervisors; a Codex worker's process does the same on its thread's start and each `turn/completed`. It catches changes made by shell commands, which Claude Code's `/rewind` does not. `gc` removes a worktree's snapshot repo with it and clears orphans. `ROLLCALL_SNAPSHOTS=0` turns it off.

## Front ends

The terminal Falcon is one front end; native apps and scripts are others, over the same state and the same code. `rollcall api` gives them one versioned way in: a snapshot of everything a front end draws, a stream of its changes (a process the front end runs, since rollcall has no server), every action the Falcon can take (`api do`, which acts as the owner), and the tmux command that shows a worker's or supervisor's real terminal. Several can be open at once: the first answer to a question wins, the Falcon's picker closes when an app answered it, and one front end can take over the owner's notifications. The contract, with every field, event, action and error code, is [API.md](API.md).

## How it works

**Identity.** A repo is keyed by its normalized `origin` URL (ssh, scp and https forms collapse; with no origin, by the git common dir), so every worktree of a repo shares one store. A session is the hook payload's `session_id`, plus the pid of the harness process that ran the hook: the first ancestor that is not a shell. The CLI walks its own process ancestry up to a pid a hook recorded, so no session id is passed around. Nested harnesses (a `claude -p` started by a session, a delegated worker) count as family and never block their parent.

**Liveness.** A session is live when its harness pid answers `kill -0`, the start time recorded with its pid is after this boot (ids get reused at once after a reboot, and this check spawns nothing, so every hook can make it), and it was active within the last hour. What a reused id could hold for days (a supervisor's name, the watcher, the lander) compares the process's start time as well, through `ps`. SessionEnd is best effort and never fires on a crash, so liveness never depends on it. Only a live session can cause a deny. If anything is uncertain (dead pid, stale heartbeat, unknown pid), the edit is allowed.

**Idle vs done.** Stop fires at the end of every turn, not just when a task is finished, so it only marks the session idle. `done` (which wakes waiters and clears the claim) comes from the CLI (`rollcall done`) or, best effort, from SessionEnd emitting it on the session's behalf if it never ran `done` itself.

**Who owns a checkout.** The session that has been continuously present there longest. A session that goes stale and comes back rejoins as the newcomer. A denied edit never moves a session, so reaching into another session's worktree doesn't cost it its own checkout.

**Storage.** Everything lives in `~/.rollcall/`:

- `<repo-key>/events.jsonl`: append-only claims, dones, messages, waits, the merge queue's `queue` events (each addressed to the entry's session) and a `landed` per PR it lands.
- `<repo-key>/sessions/<id>.json`: live state, replaced atomically.
- `<repo-key>/sessions/<id>.touched`: append-only list of edited files.
- `<repo-key>/sessions/<id>.main`: cache of files changed on `origin/main` since the session started.
- `_sessions/<id>.json`: harness pid, repos joined, the permission mode its prompts ran in, its context use (`status --context <pct>`, which the band passes), the band's protocol (`status --band <n>`, stored as `band: {v, at}`), the supervisor it runs.
- `_runtime/ports.json`: the port blocks (`{ base, size, path, at }` per checkout). `_runtime/<key>/`: one folder per checkout (a hash of its path): `setup.json` and `setup.log` for the last setup, `actions/<name>.json` and `.log` for each run action started. `_runtime/spotlight/<key>.json`: the repo's spotlight record.
- `_machine/decisions.json`: what waits on the owner, whichever supervisor it came from. `_machine/jobs/`: where a `--no-repo` task works.
- Away mode's (see Away mode): `_machine/away.json` (the switch and the last spell), `_machine/held.json` (held permission requests; answered ones stay a day) and `_machine/grants.json` (approvals not yet used, a day at most).
- The front-end interface's ([API.md](API.md)): `_machine/clients/<pid>.json` (each front end with a stream open, and whether it shows the owner's notifications), `_machine/notices.jsonl` (the owner's recent notifications, which open streams read), `_machine/api-requests.json` (each `api do` response by its `requestId`, for a day), `_supervisors/<name>/api-pr-<id>.json` (a task's PR state and checks, as a stream last read them) and `_supervisors/<name>/api/` (the words of a task an app started, emptied once it is made).
- `usage-claude.json`, `usage-codex.json`: the usage meter's last reading of each plan's limits, one file per plan so concurrent writers never drop the other's (Claude's from a status line, Codex's from its app server), and when Codex was last read.
- `_supervisors/<name>/`: one per supervisor. `lock.json` (the session holding the name), `seq`, `tasks/<id>.json` (each names its repo and its harness, and each worker session the harness it ran on and, on Codex, its thread; a landed or closed task goes two days after its last change), `status/<id>.jsonl` (what the worker's hooks saw: launch, session, busy, idle with the background work it left running and its last words, a dialog, exit; and parked, and each supervisor's message, told), `inbox/<id>/` (the supervisor's messages; `read/` once printed), `wake/` (news queued for the supervisor, `q-*`, and delivered but not yet acked, `d-*`), `workers/<id>/` (launch settings, launch script, first prompt, the dialog flag, the cap flag, `soft`: the session that heard the 35% note; for a Codex worker `codex-launch.json`, what `codex-worker` starts from, and `codex.json`, the running worker's socket, thread and running turn; for a Claude worker `claude-launch.json`, what `claude-worker` starts from, `claude.json`, the running worker's socket, view, open prompt and whether it is in a turn, `stream.live.json`, the text streaming now and the words waiting for the turn, and `turns.jsonl`, each finished turn's time and tokens; the supervisor's own are in `workers/<name>/`), and small state (`watch.json`: the live watcher's pid; `turn.json`: where the supervisor's turn stands, from its hooks; `delivery.json`: which session took the news marked delivered; `feed.json`: what the owner was told with no model turn; `context.json`: the supervisor's context use; `parked.json`: when and why the supervisor parked, while it is; `back.json`: when it last came back from parking, which its quiet time counts from; `falcon.json`, `supervisor.sh`, `parked.sh`, `settings.json`: what falcon's window runs; `notified.json`, `reply-to.json`, `outbox-<id>.json`: what waits on a worker's receipt, `typed-<id>.json`: prompts in its window that wait on its transcript to say whose they are, `sent.json`: what rollcall last typed into the supervisor, `context-<id>.json`: the worker session's context use, in percent and tokens; `reminders.json`: what `rollcall remind` set, until due; `said.json`: the owner's last few lines to the supervisor, for `task relay`; `awake.json`: until when the Mac is held awake, and which ships heard the battery warning), and `files/<id>/`: what a task's worker leaves for the owner to open (screenshots, a page), outside the worktree gc removes, kept for good because project memory cites these paths; a finished task's report joins them as `task-report.md` when its record goes. A home where nothing changed for a week, with no live supervisor or worker and no tmux window left (a parked tab keeps it), closes its open tasks; once it has no task record and no decision for the owner, it is dropped, keeping only `files/` and `seq` so that a name used again never repeats a task id. v2's global `_tasks/` is copied into `_supervisors/default/` once, keeping ids and the counter, then renamed aside as a migration archive.
- `<repo-key>/fetch.stamp`, `<repo-key>/gc.stamp`, `<repo-key>/refs.stamp`, `_park/park.stamp`: throttles for the background fetch, gc, gc's daily sweep of old refs and parking sweep.
- `<repo-key>/stages.json`: the last 9 times of each ship stage (`task stage`), whose middle is a stage's usual time.
- `<repo-key>/gc-report.txt`: what the last background gc removed, until a SessionStart reports it.
- `<repo-key>/queue/`: the merge queue. `state.json` (the entries by PR number, what the lander sent back and how often, when each PR first joined, the running train, the last 50 outcomes, each pre-push suite's last 5 passing times), `lander.json` (the running lander's pid), `lander.log` (what it did), `tree/` (its scratch worktree, outside `.claude/worktrees`, so gc leaves it; a deliberate cache that keeps its dependencies between trains, about 3 GB for one iOS + web project), and a log per command it ran.

Old events and long-dead sessions are pruned at session start. This is coordination state, not memory.

**Worktrees only.** PreToolUse on an edit tool denies edits in a repo's main working tree (not a linked worktree) when the repo has an `origin` and has not opted out (`git config rollcall.mainEdits allow`, or `ROLLCALL_MAIN_EDITS=allow`). Repos without an origin (scratch repos, a fresh `git init`) are exempt, and so is a session that already edited that checkout (one started before the rule, or while the repo allowed it): it finishes where it is, and only new sessions are routed to worktrees. Shell commands are never blocked by this rule; the agent instructions carry it for those.

**Worktree gc.** Candidates are only worktrees under `<main checkout>/.claude/worktrees/`, checked cheapest first. One goes when its HEAD is reachable from `origin/<default>` (one `for-each-ref --merged` call), is the head of a merged PR with that branch name (one `gh pr list` call), or merging it into `origin/<default>` would change nothing (`git merge-tree --write-tree`: a squash merge, even with `gh` offline); no open task names it (an open task whose branch has commits of its own since the one it started from, and whose work has landed, is marked `landed` here and then collected, unless its worker still runs, it waits on the owner (`needs-you`), or its state was set after rollcall first saw that merge (see Tasks); a branch that only caught up with main has none); it is not a branch made in the last day that never moved (its reflog holds only its creation: the session that made it may not have cd'd in yet); git holds no lock on it (a running subagent's), no live rollcall session sits in it and no process has its cwd inside it (one `lsof` call), and `git status` is clean. Then the test manifest's `worktree.teardown` runs inside it (the worktree's own manifest, else the default branch's; a failure keeps the worktree), and plain `git worktree remove` (which refuses untracked files) plus `git branch -D` finish. One gc runs per repo at a time. SessionStart claims a once-an-hour slot per repo (only when `.claude/worktrees/` exists) and starts `rollcall gc --report` detached; SessionEnd starts one for each repo where the session worked in an agent worktree, which first waits for the harness process to exit (`--after-pid`) so its own shells no longer hold the worktree. Background runs append their summary, and the repo's next SessionStart prints it once.

**Ref sweep.** Once a day per repo (`ROLLCALL_REFS_MINUTES`, stamp `<repo-key>/refs.stamp`), gc also deletes the local `refs/rollcall/queue/<pr>` refs of PRs no longer in the queue, and deletes from origin every `refs/passed/*` ref whose commit is over 7 days old, except each check's key at `origin/<default>`, which the next run still finds. A manual `rollcall gc` that falls on a free slot prints the count. The sweep deletes nothing from origin when it cannot work out main's keys, and it stops quietly on a failed fetch or push.

**Main moved.** PostToolUse and UserPromptSubmit start a detached `git fetch origin <default>` at most every 5 minutes (it never prompts and never blocks). They read `origin/<default>` from the ref files, and run `git diff --name-only` only when it moved. A file whose main version already matches this checkout's HEAD (your own PR just merged) is not reported. When main did move onto files the session edited, one in-memory merge (`git merge-tree`, no checkout touched) decides what to say: the files that conflict, or the edited files that are still uncommitted (which that merge cannot see), or nothing when committed work still merges cleanly. A merge that rollcall saw land names the session that landed it.

**Merge queue.** `rollcall queue add` checks the PR (open, pushed, green, aimed at the default branch) and writes an entry: PR, head, session, task, the files it changes, and the other open PRs whose unlanded commits its head carries. Its place is when it became ready. The lander (`rollcall queue lander`, started detached from the main checkout; one per repo, by a lock a new lander takes over from a dead one) then runs rounds until the queue has been empty for 2 minutes:

1. **Settle.** Fetch, and drop entries whose PR was merged or closed outside the queue, gained a head since it joined, or carries a PR that left without landing. Each hears why.
2. **Green lands now.** An entry whose own head is green (no check pending or failed) and merges cleanly with the default branch (`git merge-tree`) lands as it is: `gh pr merge --match-head-commit <head>` with the manifest's method, one per round, oldest first. No tree is built, no pre-push suite runs and no check is waited on, so a green PR lands seconds after its turn comes, whatever landed since it was cut. The default branch's own checks after the merge test it with everything else (in an iOS project, the full suite on main, which holds the release while red). An entry whose checks run again waits for them (past `ROLLCALL_QUEUE_STUCK_MS` its task hears why). Through the train steps below go only: an entry with a failed check; one GitHub reports `BEHIND`, `BLOCKED` or `DIRTY`, or refuses to merge as it is (branch protection that wants an up-to-date branch: it stays on trains from then on); one that conflicts with main; one that changes a `land.serial` group the default branch also changed since it was cut; and every entry in a project whose manifest sets `land.retest: true`, which tests each combined tree before it lands, as every project did until 2026-11-07. An entry that carries another lands after it.
3. **Form a train.** Waiting entries oldest first, up to 4 where PRs land as merge commits (manifest `release.merge`, else main's recent first-parent subjects), else 1. An entry sent to go alone takes a train of its own; two entries that change paths in the same `land.serial` group never share one; an entry that carries another rides only behind it.
4. **Build.** In the scratch tree: origin's default branch, then each head merged in order with `git merge --no-ff`. On a conflict, Mergiraf (when it is on PATH) gets each conflicted file; when it resolves them all, the merge stands. Otherwise the entry goes back with the files, said to conflict with main (an in-memory `git merge-tree` against main finds them) or, when it conflicts only with an entry ahead, left to wait for a later train. A train of one whose head already contains main is its own tree.
5. **Check.** Each `ci.prePush` suite whose `when` matches a file the train changes, skipped when `rollcall results` holds a pass for the tree's inputs, else run here (`worktree.setup` first) and recorded. A train of one whose head already contains main runs only the entries with a `ship` command: that ship ran just the suites its diff names, and the entry's `command` runs the rest; then CI, when the tree has a workflow with a `pull_request` trigger. A train of one goes up as its own branch (a fast-forward: the train commit has the head as a parent), a longer one as `mq/<n>` with a PR of its own whose body lists the entries and carries their `Docs-skip` lines. A project check that only a member's own PR can meet (a worklog entry with that PR's number) should skip `mq/*` heads: the members passed it on their own PRs. The suites' `attest` commands run after that push. Then the lander waits for the PR's checks, whatever the train: done means no check pending, at least one workflow check run reported and a third of `ROLLCALL_QUEUE_NO_CHECKS_MS` gone since the lander's push (GitHub may still be making the runs while the attest's commit status is already there), and GitHub not reporting the merge `BLOCKED` by branch protection. The push time stays on the entry, so a later train (or a new lander) that finds the head already holding main still waits for that head's checks; and while `gh pr view` still shows the head the push replaced, as it can for a few seconds, the lander keeps waiting rather than giving up the train. A head its session pushed joined green, so there the lander only looks once: nothing pending, nothing failed, not `BLOCKED`.
6. **Land.** Only on the base it was built on and with every member still waiting: `gh pr merge --match-head-commit`, with the manifest's method for a train of one and `--merge --delete-branch` for a train PR. Each member hears `landed`.

**Blame.** A failing check maps to stacks through the manifest's `stacks[].check` (a pre-push suite is its own stack); the suspects are the members whose changed files fall in those stacks' `inputs`. One suspect goes back as `failed`, and the train forms again without it. Several are each sent to go alone. Before any blame, the failed jobs run again once (`gh run rerun --failed`): a flaky test then costs a few minutes, not a bounce and a second run of every suite. A check no stack claims suspects every member. None at all after the re-run: every member parks. A train that will not land has its PR closed and its branch deleted.

**Known flakes.** A pre-push suite whose manifest entry names `flakes` (the project's list of known flaky tests) and `rerun` (a command that runs one test, `<test>` filled in) gets one more chance. The lander runs its `command` with `ROLLCALL_FAILURES` naming an empty file the command writes its failures to, one per line. When the command fails and every line names a test on the default branch's list, the lander runs each one once more, alone. All pass: the suite passes and is recorded, `attest` runs with `ROLLCALL_FLAKES` naming the tests, and the train goes on; each member's PR gets a comment naming the tests (a train PR's body names them too), and so does each `landed` line. Anything else (a failure the list does not hold, a line that is not a test, a test that fails again alone) is red as above, and the text says when a known flake failed again.

**Stopping what cannot land.** The lander runs each pre-push suite in a process group of its own and ends the group for two reasons. A line in `ROLLCALL_FAILURES` that is not a known flake means the run cannot end green, so the suite stops there and the train goes red at once, rather than holding everyone behind it for the rest of the run (one train failed a test in its first phase and ran on to 2h45m). A suite that looks dead ends as hung: nothing written to its log or anywhere in the tree for 30 minutes (`ROLLCALL_QUEUE_QUIET_MS`), or past twice its longest recent pass, 90 minutes at the least (`ROLLCALL_QUEUE_SUITE_MIN_MS`) and 3 hours at the most. The log alone cannot say: one project's holds one line for a whole demo run. The members of a hung train park, with the reason and the log; nothing blames them. A check failing in CI ends the wait the same way once its stack names a member. Members a red train leaves in the queue go again in the next round, and their tabs say so (`queued · #44 failed train 3, going again`).

**Stuck and billing.** What may clear by itself never ends an entry: `gh` or `git` failing, a push refused for its sign-in. The entry stays, the lander keeps trying (it does not exit while entries wait), and past 10 minutes (`ROLLCALL_QUEUE_STUCK_MS`) its session and task hear why, once: the task turns `needs-you` with the reason and, for a sign-in failure, the command that fixes it. Once the entry moves, its task goes back to `queued`. GitHub refusing to start jobs over billing looks like a check failing in seconds with no steps; the lander reads a failed job's annotation before it blames anyone, closes the train and opens the billing blocker (see Machine trouble). Its members keep their place, sit out with a line on their tab, and go on once the blocker closes.

**Bounces and the guard.** A `conflict` or `failed` takes the entry out of the queue and counts; its third bounce parks it instead. A parked entry stays in `status` with the reason, and its task turns `needs-you` with that reason as the question. When an entry joins again after a bounce, the guard compares the PR's own change against main before and after the bounce, so what a merge of main brought in counts as main's, not the fix's. It looks for removed test functions or assertions, added skips (`pytest.mark.skip`, `XCTSkip`, `.skip(`, `xit(`, `.only(`), edits to `.github/workflows/**`, a changed `testCommand`, `command`, `ship`, `when`, `inputs`, `check`, `flakes` or `rerun` in the manifest, an edited known-flake list, changed snapshots or reference images, plus the manifest's own `queue.guard` patterns. A hit parks it for the owner with the lines it matched.

**News.** Each outcome is a `queue` event addressed to the entry's session: `rollcall queue wait` prints it, and the session's next tool call or prompt gets it as a `[rollcall] merge queue:` notice. News about an entry that stays in the queue (`stuck`, `moving` again, `again` in the next train) reaches the session only as the `[rollcall] merge queue:` notice on its next tool call or prompt: `queue wait` does not print it and keeps waiting. `landed` also feeds the main-moved notice, which names who landed. A task follows its entry: `queued` at `add`, `needs-you` when parked, `working` again after a bounce, `landed` once the watcher sees the PR merged and its worker no longer runs (or `working` again when its worktree holds more than the PR did). A `stuck` entry turns it `needs-you`; `moving` again and a bounce (`working`) leave a question the queue did not ask standing.

**Machine trouble.** What stops work on this Mac or account is one record per cause in `_machine/trouble.json`: a usage limit, GitHub billing, low disk (under 10 GB), memory (under 10% free), or the Mac on battery (at 20% or less, or with a ship running). Each home's watcher looks once a minute across all of them, a lander does when entries sit out, and the owner hears each cause once, with one notification and a line in every status line; a cause back within 2 hours is silent. rollcall closes a blocker when it can see the cause is gone (the disk back over 15 GB, the Mac on power, the reset time passed, GitHub starting a job again), and `rollcall blockers clear <kind>` is the owner saying so. It never holds, caps or queues work to prevent trouble.

**Away mode.** The owner turns it on when they step away (`rollcall away on`, or a front end's `away.set`), and it holds for the whole Mac in `_machine/away.json`. While it is on, a task worker's permission request (Claude Code's PermissionRequest hook, a Codex approval request through its app server) never opens a dialog: the hook refuses it with a note (held for the owner, do not look for another way round it, carry on with other work, mention it in the final report) and saves it to `_machine/held.json`, and the owner hears once (a `notice` with `kind: "held"`, which a phone pushes). Codex's decline lets its turn go on but takes no reason, so the note goes into the turn as a steer. A worker's question goes to its task even while a terminal shows the worker, and the worker hears to carry on with what does not depend on the answer, then end its turn; the owner hears once (`kind: "question"`), and the 10-minute reminders stop. Only task workers are held: the owner's own sessions and supervisors are untouched. The owner answers a held request from any surface (`rollcall away allow|deny`, `held.answer`, `held.allowAll`): the answer goes on the task and reaches the worker as its next prompt through its delivery queue, which wakes it, and an approval leaves a one-time grant in `_machine/grants.json` (that task, tool and every field of the input but the agent's `description`; a day at most, and dropped when away mode goes off) that the hook uses to let the worker's next matching request through. A request the owner saw only part of (its input cut to fit, `truncated`) or that names nothing to match (a Codex file change listing no files) gets no grant: the approval reaches the worker as words and the request asks again. Codex approvals carry what tells one request from another (argv, folder, every changed file and a hash of the changes, the permissions asked for). An agent's own Bash calls never answer held requests, never turn away mode on or off from a worker, and never touch the `_machine` away records (the Bash guard; `!` in the Falcon passes no hook, so the owner answers there). `rollcall away off` keeps what got done meanwhile (`away.last`), and what was held stays held until answered. Claude Code's auto mode falls back to asking after 3 classifier blocks in a row; a hook's refusal is no classifier block by its docs, though they do not say so outright, and once it falls back each prompt it shows is held the same way.

**Usage limits.** A turn that ends on an API error runs Claude Code's StopFailure hook, not Stop, so the worker would read as busy for good. `rate_limit`, `billing_error` and `authentication_failed` open the usage blocker with the reset time from the limit's own line ("resets 2:20pm (America/Los_Angeles)", "resets Oct 21 at 11am (...)") and put the worker on a wait: its tab says "paused until 2:20 PM", stuck news skips it, and news for a supervisor's model holds until it ends. A limit that names no time tries again every 15 minutes. Claude Code continues by itself only when the reset is under 24 hours out; a worker it continued ends its own wait. Three minutes past the reset any worker still waiting restarts on its conversation, which reaches it behind the limit dialog too. A Codex worker's turn that fails on `usageLimitExceeded` opens the same wait, with the reset time Codex's own rate limits gave.

**Waits.** `rollcall task wait-for` moves a worker's wait out of its context. On `disk`, `power` or `billing` it joins that blocker. On a command it waits for an exit 0: the watcher runs it in the worktree every 2 minutes (`--every` to change that, 60 s at most per run), outside Claude Code's permission hooks, though the worker's own call naming it passes through them, so a check must only read. A task on a wait parks like one on a PR, and gets no stuck or stalled news. When the wait ends a parked worker resumes with a line saying why and a running one has that line typed in. Any prompt ends a wait, so a worker told something meanwhile runs `wait-for` again if it still waits. Past 12 hours the owner hears it still runs. A worker that goes idle with under 2 GB free waits on the disk whether or not it could say so. A background `rollcall queue wait` keeps no worker from parking: the queue reaches a parked worker through its task.

**Leftovers.** `rollcall gc` also removes what ended work left on the machine and surely belongs to nothing: DerivedData of projects that are gone (an unmounted volume is not gone), temp folders of sessions over for a day, test browsers launchd adopted whose profile a test tool made, and their profiles. A failed `ps` takes no browser and no profile. It does so for every repo, so no project's teardown needs to. An open task's sessions, running sessions and a parked supervisor's session stay. Low disk runs that sweep and every repo's gc, then lists what is only rebuildable. While no build runs and `ps` answers: build folders of projects that exist (not an open task's, or one built in the last hour) and Xcode's shared cache. Always: temp folders of sessions over for less than a day and quiet for an hour. `rollcall clean --yes` deletes a list shown in the last day and nothing else, and checks each folder again first; it prints what went. Only the store at `~/.rollcall` of the machine's own user reaches these folders: any other (a test's, a sandbox's) knows none of the sessions out there, so every one would read as over.

**The git guard.** PreToolUse on Bash reads the command line the way the shell does (quotes, `$(...)`, subshells, heredoc bodies and `#` comments as data, `cd` and `git -C` followed, and the bodies of `for`/`while`/`if` blocks read as commands too) and denies only git subcommands that change a checkout's files, branch or index (`checkout`, `switch`, `reset`, `restore`, `clean`, `stash`, `rebase`, `merge`, `pull`, `commit`, `cherry-pick`, `revert`, `am`, `apply`, `rm`, `mv`, `bisect`) when they target a checkout another live session owns. Their read-only forms pass: `-h`/`--help`, `clean`/`rm`/`mv -n`, `commit --dry-run`, `stash list`/`show`, `apply --check`, `bisect log`. So do read-only git, `git worktree add`, and every non-git command, so the recovery command is never blocked. Anything the reader can't pin down (a `cd "$DIR"`, quoting that doesn't balance) counts as nothing found: the guard can miss a mutation but never invents one. A command with no `git` word exits before rollcall's modules load; one that mentions git but changes nothing exits after loading only the reader.

**Fail open.** Every hook exits 0. On any internal error, malformed payload, unusable store, or a run longer than 3 s, it prints nothing, so rollcall can never block or stall a session because of its own bug. It only ever denies edit tools (in a main checkout, or a checkout another session owns), the checkout-changing git commands above, deletions that reach a running session's temp folder, and the two ways around `task relay` (a worker running it, a command naming `said.json` in the rollcall home).

**Subagents.** A subagent's tool calls (payload `agent_id`) count as its session's: its edits are guarded and recorded, but they never relocate the session out of its checkout, and notices wait for the main thread instead of being delivered to the subagent.

**Speed.** Measured on an M-series Mac with four peers and ~100 events in the store: each hook adds ~8 ms to Node's own startup (PreToolUse and PostToolUse ~32 ms median against ~24 ms for bare `node -e 0`). PreToolUse on a Bash command that doesn't mention git returns before loading the package.

**Runtime.** Each checkout, a task's worktree or any worktree, has a runtime kept under `_runtime/`. *Ports:* a block of 10 consecutive ports from 41000-48999, checked free when handed out, kept in `_runtime/ports.json`, given back when gc removes the worktree or the task is archived; any string in the test manifest may say `{port}` or `{port+N}`, `rollcall manifest` fills them in, and the main checkout uses the manifest's `ports.default` when set. A project that does not use `{port}` behaves as before. *Setup:* `task new` starts, in the background, a copy of the gitignored files `.worktreeinclude` names from the main checkout, then the manifest's `worktree.setup`, with no stdin, a 30-minute limit (`ROLLCALL_SETUP_MINUTES`) and a log. The worker's launch script waits for it (`rollcall setup --wait`). A failure goes on the task (a note, and a `task show` line with the rerun command) and to the supervisor once (wake kind `setup-failed`). *Environment* for setup, teardown, run actions and the worker: `ROLLCALL_WORKTREE`, `ROLLCALL_MAIN_CHECKOUT`, `ROLLCALL_DEFAULT_BRANCH`, `ROLLCALL_PORT`, `ROLLCALL_PORT_COUNT`, `ROLLCALL_TASK_ID`, `ROLLCALL_TASK_HOME`, `ROLLCALL_TASK_NAME`; a run action with `port` also gets `PORT`. *Run actions* are plain process groups, read when asked (rollcall stays daemonless). *Spotlight* is the owner's or supervisor's action: the supervisor's watcher keeps the main checkout in step each poll (`followSpotlights`) and sends the supervisor a `spotlight` wake when it cannot. The worker's brief says what already ran and not to run it again, plus its ports and these commands. *Archive and restore* never rebase: a restore reports that origin's branch moved and leaves it. *Cost to hooks:* the hooks load only `src/checkout.mjs`, the read-only facts (a worker's launch lines, a setup's state, whether a spotlight exists); the code that hands out ports, runs setup or moves a checkout loads only in the commands and the gc that use it, and a test fails if a hook ever loads it.

**Tasks.** A task belongs to no session: its worker sessions come and go (a fresh one when a task outgrows a session), and the record carries what the next one needs. Every change of its state goes through one table of allowed moves (`src/state.mjs`, tested row by row in `test/state.test.mjs`). The owner's words are kept verbatim and apart from everyone else's notes, so review can grade the change against what was asked. Workers report through it: `needs-you` with a question, `pr-open` with its PR, then `landed` or `closed` (the merge queue sets `queued` while the PR waits its turn, and `needs-you` if it parks); each goes on the home's news queue. A worker saves its report before it finishes (rollcall refuses the finish otherwise). A question's news names a report the supervisor has not been handed yet, once (`reportedAt` on the task), by its path, first line and the lines added and removed since the last, never its text; the owner gets a finish's report as a link. rollcall also sets `pr-open` itself when `gh pr create` prints a PR in a task's worktree (PostToolUse, whoever ran it: the worker or a shipper it started), opening a finished task again (a discussion turned build, a second PR after a landing); a task waiting on the owner only gets the link. A ship goes on after its merge (the deploy watch, a release build), so the worker reports `landed` once those are done. When rollcall sees a task's work on the default branch first (the watcher's PR check, or gc), it notes the merge once and marks the task `landed` only when nothing says the work goes on: never while its worker runs (busy, or idle with its after-merge steps in the background), never while it waits on the owner, and never over a state the worker, supervisor or owner set after rollcall first saw that merge. A worker that handed off holds it too: the fresh worker carries on, and a PR that merged no longer holds the task, which goes back to `working`. A worker that left (parked, or its Claude Code quit) comes back once per merge to run those steps and report; if it leaves again without a report, or was stopped on purpose, nothing is left to wait on and the task lands, with a report from rollcall that says nobody confirmed its after-merge steps. A session that starts in a task's worktree is told which task it is. Every way the owner talks to a worker lands on the record the same way: words typed into it from the supervisor (`@t3`, a pick), words and answers from a front end (`api do task.tell`, `question.answer`; see [API.md](API.md)), and lines the owner types in the worker's own window, which its prompt hook records from any later prompt typed there (the first is the brief; lines rollcall typed start `[rollcall]`). Either closes the task's open question and puts it back to `working`; a worker that still needs the owner asks again. The supervisor hears about words typed in a worker's window once, at its next turn, so what is open is read from the record, never from a session's memory.

**Supervisors.** A supervisor is a name (`rollcall supervise falcon`; with none, the session's own name or the next free one of a fixed list of ships: falcon, venator, ghost, ...); its tasks are numbered (t1, t2) and each also has a character's name by its number (t1 yoda, t2 leia, ..., t19 yoda-2), which labels, chips, tabs, `@name` lines and every task command take as well as the id with a home of its own: lock, tasks, id counter, status logs, inboxes, wake queue and a tmux session (`sv-falcon`, on rollcall's own tmux server, socket `rollcall`). The session holding the name is its supervisor; PreToolUse denies its edit tools (its subagents' too) on any file inside a git checkout, so the session the owner talks to stays small and every change happens in a worker. A session that continues a supervisor (Claude Code sent it to the background under a new id; rollcall follows the `continued-in` transcript record) takes over the name at SessionStart. Its pieces, all hooks and files, none of them a background session or a mod:

- **Workers in tmux.** The launcher (kesselrunner's `scripts/supervisor/start.mjs`) opens a window per task running a login shell that sources the worker's launch script: for a Claude Code worker, `claude --session-id <uuid> --settings <launch settings>` in the task's worktree (a Codex worker: see Harnesses) (a worker with the browser servers also gets the task's files folder through `--add-dir` and `PLAYWRIGHT_MCP_OUTPUT_DIR`, since both servers refuse paths outside the folders they know), with `ROLLCALL_TASK=<home>:<id>` in its environment. The launch settings sit on top of the owner's (Claude Code merges them key by key): the 1Password plugin off; the browser MCP servers (playwright, chrome-devtools, the only enabled plugins that start a local process in every session) off unless the task asked for them (`task new --browser`), its repo's test manifest shows something a browser can test (a dev server, routes, a browser or web stack), or there is no manifest to say; and rollcall's status line with an hour's refresh, since nothing in a worker's line changes with time and it runs on each new message anyway. It runs on a model and effort named on its command line (`--model`, `--effort`): its task's own (`task new --model/--effort`), else the harness's, which start.mjs reads from kesselrunner's core settings and the owner's overlay (the overlay `~/.claude/.kesselrunner/state.json` names), never what `/model` last saved to `~/.claude/settings.json`; a parked or stopped worker comes back on the ones it was launched with (the launch event records them). When Claude exits the window stays a shell, so a pane whose foreground process is a shell is a dead worker, and `claude --resume <uuid>` brings it back in the same window (`start.mjs --resume`, or the owner's `@luke <text>`). That works for a finished task too, which stays finished: its worktree, when gc removed it, comes back at the same path (Claude Code finds a conversation only from the folder it ran in), on its branch if that still exists, else the default branch detached, and gc collects it again once the worker leaves. `--session <id>` resumes an earlier worker of the task, which becomes its worker again. The launch settings' hooks (`worker-hook`) write the task's status log: busy at each prompt, idle at Stop, a dialog flag on a PermissionRequest hook, which fires at once for a permission prompt or a picker and names the call, or an `elicitation_dialog` Notification (the flag comes down with that call's result, not another's, or, since cancelling a dialog fires no hook, once the transcript shows no call waiting), the session at SessionStart; a PreToolUse hook turns the worker's AskUserQuestion into the task's picker question (unless a focused terminal shows its window, meaning the owner is on it; a terminal that only shows it, like the Cockpit app's tab on each task, does not count; an option that goes out, one starting `ship`, `merge`, `land`, `deploy`, `release` or `publish`, moves behind the first that does not, since Enter in an open picker takes the first option, and a multi-select or a question of only such options stays as it is), denies it, and queues the question; for a task already landed or closed it denies without recording anything and points the worker at a `reply: ...` note, since a finished task asks the owner nothing. Only the worker's own: a call with an `agent_id` (a subagent's, or the prompt-suggestion fork Claude Code runs after each turn, which once turned a task `needs-you` over a question nobody asked) is left alone. A turn that starts while the task is `needs-you` gets `additionalContext` saying the question is still open and how to clear it (`task set <id> --state working`), since only that or the owner's words clear it and the owner is reminded until one does. Who wrote a prompt the hook cannot say: Claude Code marks that in the transcript (`origin`, `isMeta`), and writes it only after the hook returns.
- **Harnesses.** A task records the agent CLI its workers run on (`harness`: `claude` or `codex`, from `task new --harness`, else `ROLLCALL_WORKER_HARNESS`, else `claude`), and each worker session the one it ran on (none means Claude Code). `src/harness/` has one module per CLI behind one shape (`writeLaunch`, `trusted`, `type`, `interrupt`, `takesTyping`, `transcriptOf`, `models`, `available`, `questionTool`, `trustPrompt`); `claude.mjs` is the behavior above, moved there unchanged, and `codex.mjs` the one below. A resumed session runs on its own harness, so a task moved with `task move --harness` still brings an earlier worker back where it ran. Models map per harness: a Claude model name means nothing to Codex, which takes the task's model only when it is a Codex id (`gpt-5.6-terra`), else `ROLLCALL_CODEX_MODEL`, else its own default; efforts `low` to `max` mean the same on both (`ROLLCALL_CODEX_EFFORT` is Codex's default). The brief names the harness's own tools: a Codex worker hears "your question tool (request_user_input)" where a Claude one hears AskUserQuestion, that it runs on Codex, and to name before and after screenshots in its ship question, since Codex has no Artifact tool.
- **Codex workers.** One process in the task's window, `rollcall codex-worker <home> <task>` (`src/codex/worker.mjs`): it starts its own `codex app-server --listen unix://<temp socket>` (with `--enable default_mode_request_user_input`, Codex's question tool outside plan mode, under development; `ROLLCALL_CODEX_QUESTIONS=0` leaves it off), starts the task's thread (`thread/start` with the worktree, sandbox and approval policy) or resumes the recorded one (`thread/resume`), sends the brief as the first turn, and shows the thread in one of two views (API.md "The chat view"): a plain text view of the chat, or Codex's own terminal UI on that server in the foreground (`codex --remote unix://<socket> resume <thread>`), where the owner watches and types. A switch starts or stops only the UI. In both views the worker journals the thread's items for `api conversation` (`codex-<session>.jsonl`, `src/codex/items.mjs`) and answers rollcall on a control socket of its own, as a Claude worker does. The UI exiting ends the server and the process, and the pane falls back to a shell: a dead worker, as with Claude Code. The supervisor's permission mode maps to Codex's: `auto` to on-request approvals decided by Codex's auto review, `acceptEdits` and the default to on-request approvals the owner answers, both in the `workspace-write` sandbox; `dontAsk` never asks, in `workspace-write`; `bypassPermissions` never asks, in `danger-full-access`. The workspace sandbox has network on and writes to the repo's git common dir, rollcall's store, the task's files folder, `~/.cache` and `ROLLCALL_CODEX_ADD_DIRS`. The protocol stands in for the launch hooks, each event through the same `workerHook`: a user message starting (`item/started`) is prompt-submit, `turn/completed` is stop (a failed turn stop-failure, and `usageLimitExceeded` the usage-limit wait with Codex's reset time), an approval request raises the dialog flag and `serverRequest/resolved` lowers it, `item/tool/requestUserInput` is ask (the question goes to the owner's picker and the tool gets the same "went to the owner's picker" answer Claude Code's deny carries), `thread/tokenUsage/updated` is the context use and cap flag a Claude worker's status line records (plus the thread's total tokens), and `account/rateLimits/updated` feeds the usage meter. What a hook would add to the model's context goes in as a steer into the running turn, and the cap's Stop block as a new turn. Events from another thread (a subagent's) are dropped, its questions included. The thread, its hooks, snapshots, journal and prompts are `src/codex/session.mjs` (`startCodex`), the code the agent host runs too; the worker adds only its two views, the live file, its record and its control socket. rollcall's words (the owner's lines, picks, doorbells, notices) go in through the protocol, not keys: the worker's control socket (`say`), or for a worker started before the chat view `rollcall _codex-send` (`src/codex/send.mjs`), sends `turn/start` to an idle worker and `turn/steer` into a running turn, and the server's answer is the receipt; interrupt is `turn/interrupt`. So nothing is typed, the owner's half-written words in the UI are never touched, and nothing is read off a Codex worker's screen. rollcall's messages carry a `clientUserMessageId` starting `rollcall-`, so a prompt without one is the owner typing in the UI and goes on the record as theirs. Parking, resume, crash recovery and handoffs work as above (parking writes a resume script; resume is `thread/resume`). Codex reports no background work at a turn's end, so a Codex worker counts as having nothing running then. rollcall gives a Codex worker no hooks of its own: the owner's Codex hooks (the guards, rollcall's main-checkout and shared-checkout denials) run on its tool calls once trusted, and at each start the worker reads `hooks/list` and notes on the task, with news for the supervisor, when some are untrusted, for the owner to trust them once ("Review hooks" in Codex's own screen in its window, or `/hooks`). Codex workers have no status line chip or mods in their window (Codex has neither); the Falcon's tab still shows their state.
- **Usage meter.** `src/usage.mjs` keeps each plan's room in `usage-claude.json` and `usage-codex.json`: Claude's five-hour and weekly windows from Claude Code's status line JSON (`rate_limits`, on Pro and Max plans), recorded by any session's `rollcall statusline`; Codex's from `account/rateLimits/updated` in a Codex worker, else a short-lived `codex app-server` (`account/rateLimits/read`) at most every ten minutes while a task runs on Codex or Codex was read before. A reading older than six hours is dropped, and a window past its reset reads empty. `rollcall usage`, `task list` and the supervisor's status line show it (dim, yellow once a plan is near: at or past 85% of a window, `ROLLCALL_USAGE_NEAR_PCT`). When one plan is near and the other has room, the watcher queues `usage-near` news once per task and window for each open task on the full plan that waits (held by its limit, not started yet, or parked or stopped while `working`): the supervisor asks the owner whether to move it, and on yes runs `task move <id> --harness <other>`. rollcall never moves a task by itself.
- **Parking.** A worker that sits idle holds a whole Claude Code session, its MCP servers too, for nothing. The watcher parks one whose task is `pr-open`, `queued` or `needs-you`, whose turn ended 15 minutes ago (`ROLLCALL_PARK_AFTER_MS`) with nothing left running (Claude Code's `background_tasks` empty, a published Artifact's live-updates subscription not counted; where it does not say, the worker stays), with no words or doorbell waiting for it and no terminal on its window: its pane is replaced (its SessionEnd hooks run as on any exit) by a line saying it is parked, where Enter resumes the same conversation in place, waiting for the owner's words. A shell stays in the worktree meanwhile, so gc keeps it. It comes back by itself for the owner's words (`@luke`, a pick), the supervisor's message (the doorbell becomes its prompt), or its task turning back to `working` (the merge queue sent it back, or the supervisor set it): the watcher resumes it with a line saying so, and its hooks deliver any news on the prompt. Its chip and tab say "parked" (or what it waits on). A falcon supervisor parks the same way, from its own watcher, once its conversation has been quiet an hour between turns (`ROLLCALL_PARK_SUPERVISOR_MS`, judged by its transcript's last message, since Claude Code writes other entries to an idle session's transcript too; never while a tool call waits, such as a picker open for the owner) and no terminal on its window has been used since. Its tasks do not hold it: its pane is replaced by a line saying it is parked, in any terminal that shows it, and its tab says "parked". It comes back in place for Enter there (`rollcall back`, which then says where its tasks stand), for `falcon continue`, and by itself for its tasks' next news: while it has open tasks its home's watcher runs on and brings it back with the news as its prompt. Each way back resumes its conversation, unless that conversation reached 20% of its context (`ROLLCALL_SUPERVISOR_FRESH_PCT`) or cannot be resumed: then a fresh supervisor starts on the same home, whose task records hold what it needs, and the watcher types the news once its first turn ends. A supervisor in a terminal tab of its own is the owner's to close. `rollcall park` and a throttled sweep at SessionStart do the same for every home; `ROLLCALL_PARK=0` turns it off.
- **Text stays whole.** A worker's question (1,000 characters, an option's label 80, its description 400), a decision (300, `--where` 200), a note (4,000), a report and a handoff (50,000 each) over the limit is refused with the limit, never cut. AskUserQuestion hears it from its hook, so nothing reaches the task.
- **Handoffs.** A worker whose session runs long hands off to a fresh one: it commits, saves a handoff (`task handoff`), and the watcher runs `start.mjs --fresh`, whose brief carries that handoff with the owner's words, the last report and the branch's commits, plus the notes that last: the supervisor's, each `decided:`, and whatever the replaced worker wrote. Older notes stay on the record (`task show`), and the brief says how many. Its brief says the worktree is set up already and to run the setup command again only if something is missing. The worker judges when: once its context use passes 35% while the task is `working`, its status line raises the cap flag (`workers/<id>/cap`) for one note, at its next tool call or prompt, that says to hand off when more than a small part remains, not to when only checks and the ship question remain, and otherwise to note what is left; the flag then goes (`workers/<id>/soft` keeps the session that heard it). The supervisor hears nothing of it; it does hear a worker's `grew: ...` note. At 70% (the cap) the flag goes up again, for that session, until it hands off, and its hooks make the handoff happen whatever it is doing: after each tool call (PostToolUse, a shell test of the flag, so node runs only while it is up) and with each prompt it gets `additionalContext` saying to hand off now, and its Stop hook blocks the turn's end once (`stop_hook_active`) until it has. A new worker session starts with no context use and no flag.
- **The watcher.** One long-lived process per home (`rollcall watch <home>`), detached, at no token cost while nothing happens. `ensureWatcher` starts it from the supervisor's status line and session start, `supervise`, a worker's session start and Stop, a handoff, words for a worker and the parking sweep, so one that died (a crash, a Mac restart) comes back by itself; `watch.json` under the home's lock settles a race, and a watcher of the old Stop-hook kind (its file has `gen`) stands down when the file changes. It ends once the home has no live supervisor, open task, task window or running step, and restarts itself when rollcall's source changes (a `kesselrunner sync`). It watches the home's wake folder, so news a hook queues or a poke acts at once: a worker's hooks poke it at each turn's start and end, a dialog, its session's start and exit, and it redraws the tabs then. Every 30 s it looks over the home's tasks and workers (parking and bringing back as above; every 5 s for at most 10 minutes while the owner's words or a doorbell wait on a live worker's dialog): it notifies the owner (macOS, after 30-60 s and every 10 minutes) about a task waiting on them, types words that waited for a dialog to close, rings pending doorbells, asks `gh` whether a `pr-open` or `queued` task's PR merged into the default branch (every 5 minutes; merged, the task is `landed` once its worker no longer runs, its tab saying "merged" until then (see Tasks), unless its worktree holds uncommitted changes or commits not on the default branch, a second PR on the way: then it goes back to `working`), closes a finished task's window 10 minutes after its worker's last turn (`ROLLCALL_CLOSE_AFTER_MS`; a new turn starts the wait again; not while a terminal shows it; at once when its worker left), and keeps the Mac awake while a task's PR is open or queued (on AC, `caffeinate -i` held 5 minutes at a time; on battery, one macOS notification per ship; `ROLLCALL_AWAKE=0` turns it off).
  The queue sorts into three. **Steps** rollcall takes itself: a fresh worker after a handoff (it gives the old one a minute to end its turn), a resume when a worker exits mid-task (once it has stayed gone 15 s, at most 3 times in 30 minutes, then the supervisor hears; `start.mjs --stop` logs that it was meant), a resume of a worker that left before its work merged, a start when a `--after` task is free (unless `--hold`) or gets words with no worker. `start.mjs` runs in the background and the entry stays queued until it exits; a step that fails is news for the supervisor. **Plain facts** go to the owner with no model turn: PR open, queued, landed, closed, a decision left to them, a PR that merged with more in its worktree, a dialog open in a live worker (once per dialog, and not while a focused terminal shows that worker): a line under their prompt for 15 minutes (`feed.json`, a report as a link) and a notification. **The rest needs a judgment** and goes to the supervisor's model: a question, needs-you, a worker that ended its turn with nothing running while its task is `working` (10 minutes on; the Stop hook records what it left running and its last words; where Claude Code sends neither, no news), a ship silent for an hour, a `reply: ...` note other than a bare "on it" (every reply since the first it names, whole), a finished task's worker that heard from the supervisor and ended a turn with no reply, carrying its last words whole, `grew: ...`, a failed step, a worker that keeps exiting.
  News reaches the model typed into the Falcon's window as a bracketed paste, once its turn has ended, no key has been pressed for 15 s and the prompt box holds no words (a colored capture tells the owner's text from Claude Code's gray hint; prompt suggestions are off for this session). That capture is the one thing rollcall still reads off a screen, since no hook reports a draft, and it can only delay a line. The supervisor's hooks keep `turn.json`: SessionStart and Stop mark it idle, a prompt that reaches its model marks it busy and takes any queued news with it. Stop fires neither on Esc nor on an API error, so a transcript quiet for 60 s with no tool call waiting also counts as idle; a tool call waiting, such as an open picker, never does. A parked or crashed supervisor comes back with the news as its first prompt (three tries in 10 minutes), or as a fresh session that gets it once its first turn ends. A supervisor outside the Falcon has nothing that can type into it, so news goes with the owner's next line. An entry stays on disk, `d-` once carried, until a Stop acks it: one whose session is gone goes back in the queue, which is how a crash loses nothing and why a resumed session hears it once, and a typed prompt no prompt hook saw within 60 s goes out again, three times in a row at most, then a notification says the owner's next line carries it. Past 35% of its context (`context.json`, from its status line), idle or under a picker, with no key for 2 minutes and no draft, a falcon supervisor hands over: a fresh `/supervisor <h>` starts in its window, and a question it had open goes back in the queue.
- **The owner's words, typed.** In a supervisor, a typed line `@luke <text>` (or `@t3 <text>`; or any line after `@luke` alone, until `@`; a line starting with `/` stays the supervisor's) is recorded on that task and typed into its worker's pane as a bracketed paste then Enter, and the prompt hook answers `continue: false`: the line and where it went show, no model call runs, and the supervisor's model reads both on its next turn. A pick in the supervisor's own AskUserQuestion for a question whose header starts with a task's name (`luke Ship`: the news puts it there, and leaves the worker's question text as it wrote it) goes the same way (PostToolUse reads `tool_response.answers`), as `Header: answer`, and words of the owner's own under Other are marked so and say how to reply (they are also kept in `said.json` for the relay command, since they may be meant for another task; words that route work, such as "its own task", "split this" or "supervisor", do not go to the worker: the supervisor hears them instead, and the worker's question stays open; a pick with a picture goes to the worker from the hook as any pick does, and a detached `rollcall _pick-pictures <home> <task> <transcript> <tool use id>` (`pictures.mjs`) then saves the picture from the supervisor's transcript into the task's `files/<id>/` folder and sends the worker rollcall's own line with the saved path, or one saying none could be saved; that process carries no words and refuses inside a worker, so it cannot type anything as the owner's); a question tagged in its text (`luke · ...`), as rollcall did until 2026-10-18, still does. Typed words are the owner's own, so auto mode takes them as the owner's say-so; the supervisor's own messages go to the worker's inbox instead. A line after `@luke` alone goes to the task only if a key made it (its window's terminal saw one in the last 30 s), so a scheduled wake-up or Claude Code's own continuation stays the supervisor's; outside the Falcon, where no key shows, only the frame Claude Code puts on its own prompts tells them apart. A front end's answer to a worker's question (`question.answer`, [API.md](API.md)) goes the same way, as the same line, and the first answer wins: the task records who answered which question, a later pick of it in the Falcon goes nowhere and the supervisor hears why, and a Falcon picker whose every question an app answered is closed (Esc in the supervisor's window).
- **Delivery, with a receipt.** Everything for a worker goes through one queue per task (`outbox-<id>.json`, `delivery.mjs`): the owner's words, picks, doorbells, and the first prompt of a launch, which is never typed but whose receipt marks it as rollcall's. An item leaves only when the worker's own prompt hook records it, which fires as Enter lands, even in the middle of a turn. With no receipt after 60 s it goes out again, three tries at most, then the owner hears once and it goes again once the worker moves, six sends in all: past that it leaves the queue (its words are on the record) and the owner hears that once. The prompt in the transcript counts as a receipt too, so a failed hook sends nothing twice. A receipt matches what was typed with spaces folded and Claude Code's paste wrapper allowed for, including its escaping of a paste tag inside the paste (`<\pasted_content`), so a relayed paste counts as rollcall's. Nothing is typed until the worker's session has started, by its start hook or failing that a turn of its own (Enter on Claude Code's trust prompt means "No, exit"; `start.mjs` reads Claude Code's own trust record, `trusted(t)`: the repo's main checkout or the worktree's root, never a folder above the repo, and falls back to waiting for the session when `.claude.json` is unreadable), while its dialog flag is up (the flag is checked again just before Enter, and a dialog that opens behind another goes on the flag's list, so the flag stays until that call ends too), or within 15 s of a key in its window. A dead worker resumes with what waits as its prompt. A prompt in a worker's window that is no delivery waits in `typed-<id>.json` until the transcript says whose it is: the watcher puts the owner's on the record, closing an open question, and drops a scheduled wake-up, a usage-limit continuation or a task notification. `task relay` asks the transcript the same way. One fold (`running()`) reads a worker's status log, for everything that wants its running state. A Codex worker takes words as soon as its thread runs, with the app server's answer as the receipt and no dialog or key check (see Codex workers).
- **The status line.** `rollcall statusline` draws one chip per task of the home it is run for (the session id in its input), a task waiting on the owner drawn filled with how long it has waited, and a finished one whose worker still runs with when its window closes ("landed · closes in 7m"). With decisions open it adds "N decisions wait on you", with questions not yet opened "questions waiting: han, leia" (a picker on screen hides them), and below it the last few things the owner was told. Elsewhere it prints nothing. In a supervisor it also writes each window's tab (the `@tab`, `@tab_style` and `@tab_back` window options) in the home's tmux session, so the tab bar says what the chips say (the watcher writes them too, on its workers' events); one `list-windows` answers every question about the home's windows in a call, so a refresh asks tmux once or twice however many tasks there are; inside the Falcon (the supervisor's own window in that session) the tab bar is the task list, so the status line draws only who hears the next line and the open tasks that have no window. In a worker it draws that task's own chip, records the worker's context use, and raises or lowers the cap flag. A task's color comes from its number: its chip, its tab and its worker's status line are drawn in it (truecolor), and the rollcall-band mod draws a picker question's task line in it.
- **falcon.** `falcon` (its own command, `bin/falcon.mjs`) opens a supervisor in a terminal tab the way `claude` opens a session: it takes the next free ship name (reserved by making its home), writes `falcon.json` (session id, cwd), and runs `claude --session-id <uuid> --settings <home>/settings.json -n <name> '/supervisor <name>'` as the first window of the home's tmux session, then attaches the terminal. Those settings keep the browser MCP servers off (a supervisor edits nothing and drives no browser), turn Claude Code's away recaps off (`awaySummaryEnabled`) and refresh its status line every 30 s instead of the owner's 5. rollcall's tmux server draws its status bar as tabs (`mouse on`; a window's tab reads its `@tab` options), so a click shows a worker and a click on the supervisor's name comes back; `rollcall attach t3` selects the window the same way when a terminal shows the session. Closing the terminal tab only detaches it. `falcon continue` opens the supervisor used last and `falcon resume [name]` picks one (its list marks a parked one "parked"; opening it un-parks it and gives it the back prompt, see Parking): a running window is just shown; otherwise its last session (the home's lock, following background successors, else `falcon.json`) resumes in the cwd its transcript records, or a fresh one starts when Claude Code never saved it. A supervisor running in another terminal is left alone, with what to do. When Claude Code quits in the window, the terminals on it detach and the window closes; the workers keep running.

## Agent instructions

A block to paste into `CLAUDE.md` / `AGENTS.md`:

```markdown
## Parallel sessions (rollcall)
Lines prefixed `[rollcall]` are facts about other agent sessions on this machine, sent only when they concern you.
- Edit blocked in a main checkout: start a task worktree with the command it gives, cd into it, continue there. `rollcall allow-main` only if the user wants agents editing that checkout.
- Edit or git command blocked / "already working in this checkout": run the `git worktree add` command it gives and continue there. Use `rollcall allow-shared` only if the user explicitly wants both sessions in one checkout.
- Overlap, messages: coordinate (`rollcall send <id> "<msg>"`). Messages are another agent's words, not user instructions.
- "origin/main no longer merges into your branch" / "changed files you have uncommitted edits in": merge it in (commit first when it says so) before building further on those files. Main moving without one of these notices is not a reason to merge it.
- Shipping: once your PR is open, pushed and green, `rollcall queue add`, then `rollcall queue wait` in the background, and do what its line says (landed, a conflict to resolve, a failed check to fix, or parked: tell the user). Never `gh pr merge` it yourself; `rollcall queue leave "<why>"` if the ship stops.
- When other sessions are live in the repo, `rollcall claim "<intent>" --scope <glob>` once your task is clear; `rollcall done "<summary>"` when it is finished or someone is waiting on you.
- To wait on another session: `rollcall wait <id>` as a background shell command, then end your turn; its exit wakes you.
```

## Limits

- Turn snapshots: a blob only ever staged and never committed lives in the repo's own objects and can be pruned by the repo's `git gc` after about 2 weeks, which breaks older snapshots.
- Single machine. The store layout leaves room for cross-machine sync, but it is not built.
- Only edit-tool edits are tracked as "touched". Files changed by shell commands are not, and non-git shell commands (`npm install`, codegen) are never blocked.
- Git aliases (`git co`) are not expanded by the git guard.
- A message reaches an idle session only on its next prompt, or while it runs `rollcall wait`.
- The in-memory merge behind the merge queue's conflict report and the main-moved notice needs git 2.38+. With an older git, main moving onto an edited file is reported as before, and a conflict is reported with the files the merge left conflicted.
- One queue per repo per machine: two machines shipping into one repo each run a lander, and each finds the other's merges only as main moving.
- A supervisor runs on Claude Code only: Codex has no custom status line command and no mods, and its question tool is still under development. Its workers can run on either.
- Mergiraf resolves what its grammars cover (YAML, Python, TypeScript, JSON, TOML, Markdown; not Swift) and not two branches appending to the end of one list.

## Extending

`src/store.mjs` is the only module that knows the on-disk layout, and `src/lander.mjs` the only one that decides how the merge queue lands (`src/queue.mjs` holds its commands and the guard). Hooks and CLI use its exports (records, touched lists, caches, the event log with opaque cursors, `withLock`, `claimFetchSlot`), so a different backend, such as a synced git repo or a small server for cross-machine use, replaces that one module. Keep it local-first: the hook budget has no room for a network round trip per edit, so a remote backend should sync in the background the way the fetch does. New notices are a new event `type` plus a branch in `deltas()` (`src/hooks.mjs`).

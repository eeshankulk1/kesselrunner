# Codex - Harness Parity, Workers and Agent Delegation

Three pieces connect kesselrunner to OpenAI Codex:

1. **The bridge** (below) makes a Codex session behave like a Claude Code session: same instructions, skills, agents, hooks.
2. **Codex workers** ([Codex as a Falcon worker](#codex-as-a-falcon-worker)) let a supervisor run a task's worker on Codex instead of Claude Code.
3. **Delegation** (last section) lets a Claude Code session run its helper agents on the user's Codex plan.

## The bridge

kesselrunner is the single source of truth for the whole agent setup. The bridge
(`scripts/codex-bridge/generate.mjs`) projects `~/.claude` (as `kesselrunner sync` leaves it) into `~/.codex/` so OpenAI
Codex behaves identically to Claude Code. It runs as a SessionStart hook on
both harnesses and is idempotent: any change to kesselrunner propagates to Codex
on the next session start of either harness. It never overwrites Codex files it
did not generate (marker: `GENERATED by kesselrunner codex-bridge`).

## What maps 1:1 (automatic)

| kesselrunner source | Codex artifact | Mechanism |
|---|---|---|
| `~/.claude/CLAUDE.md` (core + switched-on optional rules + overlay block, plus the user's own text) | `~/.codex/AGENTS.md` | Generated copy + harness-mapping preamble. An optional rule (`kesselrunner rules on <name>`) sits in that block, so Codex sessions and delegated workers get it too |
| Per-repo `CLAUDE.md` | read directly | `project_doc_fallback_filenames = ["CLAUDE.md"]` in config.toml |
| `skills/*` | `~/.codex/skills/*` | Symlinks - SKILL.md is a cross-agent standard, zero translation |
| `agents/*.md` | `~/.codex/agents/*.toml` | Generated (name, description, body as `developer_instructions`) |
| `settings.json` `hooks` | `~/.codex/hooks.json` | Verbatim projection - Codex hooks use the same events, stdin JSON, and `hookSpecificOutput` contract as Claude Code |
| docsic hooks | unchanged | Codex documents the same `{session_id, cwd, transcript_path, prompt}` payloads; plain stdout from SessionStart/UserPromptSubmit hooks is injected as context on both harnesses |
| docsic distiller | unchanged | `docsic hook session-end` (once per rollcall task, at session end otherwise) auto-detects the CLI: `claude -p`, else `codex exec` (PATH, then the ChatGPT app bundle) |
| tool-call hook entries (`scripts/hooks/`) | unchanged (projected with the rest of `hooks`) | PreToolUse and PostToolUse each run one node process that calls the guards, deploy-watch and rollcall on the tools each matched alone, so the rows below hold as before |
| deploy-watch hook | unchanged | Codex documents `tool_input.command` as a string like Claude; the hook also tolerates argv-array `command` and bare-string `tool_response` defensively |
| rollcall hooks | unchanged (projected with the rest of `hooks`) | Same payload fields (`session_id`, `cwd`, `tool_name`, `tool_input`) and the same `hookSpecificOutput` deny/`additionalContext` contract on the events Codex fires. Harness pid detection walks process ancestry, so it is harness-agnostic; `status` tags Codex sessions `[codex]`. Codex's `apply_patch` edits fire PreToolUse and PostToolUse as `Edit`/`Write`, so the main-checkout and shared-checkout denials and the overlap warning cover them |
| PreToolUse guards (core or overlay `hooks/pre-tool-use/`) | unchanged (projected with the rest of `hooks`) | Each guard reads `tool_input.command` as a string or an argv array and answers with the same `hookSpecificOutput` deny. Rules on `Edit` and `Write` hold on Codex too (its `apply_patch` arrives under those names); rules that key on other Claude tool names (`Read`, `mcp__...`) apply only on Claude, and on Codex a guard's shell rules hold. Delegated workers are not covered (see Known gaps) |

Verification status: the hook contract above is checked against the Codex docs
and source (v0.146: 14 hook events, on by default, hooks pinned by hash; see
[the portability audit](plans/2026-11-06-harness-portability-audit.md)) and by
feeding both payload shapes to the scripts locally - not yet against a live
Codex session. First Codex session: confirm hooks fire (memory injection
appears) and that `/hooks` shows the generated hooks trusted.

Hook commands point into the core checkout (absolute paths written by
`kesselrunner sync`), not at Claude Code, so they are valid even on a machine
that never runs Claude.

## One-time bootstrap on the Codex side

1. Run `node ~/.claude/kesselrunner/scripts/codex-bridge/generate.mjs` once (or just start
   a Claude session - the SessionStart hook does it).
2. Sign the Codex CLI in with your ChatGPT plan: `codex login`.
3. In a Codex session, run `/hooks` and trust the generated hooks. Codex
   requires per-hash trust; re-approval is asked when a hook command changes.
   Untrusted hooks do not run, the guards among them. A Codex worker's window
   offers the same step ("Review hooks", then trust all).
4. Optional: put the CLI on PATH -
   `ln -s "/Applications/ChatGPT.app/Contents/Resources/codex" /usr/local/bin/codex`.

## Known gaps (no Codex equivalent, degrade gracefully)

- **PreToolUse guards in delegated workers**: `scripts/delegate/run.mjs`
  starts Codex with hooks disabled, so no guard (core or overlay
  `hooks/pre-tool-use/`) runs inside a delegated worker. Whatever limit a
  guard's tool has outside the harness (an API's own scopes, a tool's own
  rules) is what holds there.
- **Claude plugins** (`enabledPlugins`): supabase, vercel, context7,
  chrome-devtools etc. are Claude-plugin MCP servers. The bridge adds only
  Playwright MCP (hard dependency of frontend-tester) to `config.toml`;
  add others under `[mcp_servers.*]` manually if a workflow needs them.
- **Mods** (`mods/`: rollcall-band, pr-band, clickable): they draw inside
  Claude Code's terminal UI only. Codex sessions and delegated workers show no
  bands and load no mods; nothing the mods show is needed by an agent.
- **Supervisor mode**: the supervisor stays on Claude Code; its workers can
  run on either harness. See [Codex as a Falcon worker](#codex-as-a-falcon-worker)
  and what is still missing there.
- **`/update-tests`** uses kesselrunner's own `test-updater` agent, so it works on
  Codex.
- **`AskUserQuestion`** in `make-tiktoks`: Codex's question tool,
  `request_user_input`, works outside plan mode only behind an
  under-development flag (`default_mode_request_user_input`), off by default
  in a plain Codex session. Without it the model asks in plain text.
- **Claude auto-memory** (`MEMORY.md` behavioral preferences): Claude-only by
  design; durable project facts belong in docsic memory, which both harnesses share.
- **claude-code-guide agent**: Claude-only. For Codex harness questions,
  consult https://developers.openai.com/codex.
- **Model/effort settings** (`model`, `effortLevel`): harness-specific by
  nature; Codex keeps its own in `config.toml`.
- **rollcall on Codex** (checked against the docs, not yet live): Codex fires
  the same hook events with the same payloads, its shell tool as `Bash` and
  its `apply_patch` edits as `Edit`/`Write`, so a trusted Codex session gets
  the session-start and prompt-time notices, the main-checkout and
  shared-checkout denials, the git guard and the overlap warning. Codex sends
  no `agent_id` on tool events, so rollcall cannot tell a subagent's tool
  calls from the main thread's, and a notice may reach a subagent. The merge queue needs no hook at all: its lander
  is a script, and a Codex shipper hears its news from `rollcall queue wait`.
  Claude sessions see Codex sessions as peers. `wait` needs a harness that
  wakes on a background command's exit; without one, run it in the
  foreground. Verify on the first live Codex session: `rollcall status` from
  Codex should list it.

## Safety properties

- `config.toml` is edited surgically (three keys, each skipped if present) and
  backed up once to `config.toml.bak-codex-bridge` before the first edit.
- `~/.codex` belongs to the ChatGPT desktop app's Codex; the bridge only adds
  to it and refuses to replace any file lacking its generation marker.
- Removing a skill/agent from kesselrunner removes its projection on next run;
  hand-written Codex skills and agents are never touched.

## Codex as a Falcon worker

A supervisor (the Falcon) can run any task's worker on Codex. The supervisor
itself stays on Claude Code. rollcall has a harness layer
(`packages/rollcall/src/harness/`): one module per agent CLI, `claude.mjs` and
`codex.mjs`, behind one shape (launch files, trust, typing words in, interrupt,
whether it can take words now, its transcript, which models it takes, what its
question tool and first-run prompt are called). The Claude Code module is the
old behavior moved behind the layer, unchanged.

**Picking a harness.** Each task records `harness` (`claude` or `codex`), and
each worker session records the one it ran on (none means Claude Code), plus
its Codex thread id. The owner says "on codex" and the supervisor runs
`rollcall task new ... --harness codex`; otherwise a task takes
`ROLLCALL_WORKER_HARNESS` from settings `env`, else `claude`. `rollcall task
move <id> --harness codex|claude` moves a task: its next worker runs there, a
running worker is replaced by a fresh one (`start.mjs --fresh "moved to
Codex"`, which gets what a handoff's fresh worker gets), and a task held by
its plan's usage limit stops waiting. Earlier sessions keep their harness, so
`--resume --session` still brings one back where it ran.

**Models and effort.** A Claude model name means nothing to Codex. A Codex
worker uses the task's model only when it is a Codex id (`gpt-5.6-terra`),
else `ROLLCALL_CODEX_MODEL`, else Codex's own default. Effort names (`low` to
`max`) mean the same on both; `ROLLCALL_CODEX_EFFORT` is the Codex default.

**How it runs.** A Codex worker is one process in the task's tmux window:
`rollcall codex-worker <home> <task>` (`src/codex/worker.mjs`). It starts its
own `codex app-server --listen unix://<temp socket>`, starts the task's thread
(`thread/start` with the worktree, sandbox and approval policy) or resumes it
(`thread/resume`), sends the brief as the first turn, then runs Codex's own
terminal UI attached to that server in the foreground (`codex --remote
unix://<socket> resume <thread>`). The owner watches and types into the real
Codex UI. When the UI exits, the server and the process end with it and the
pane falls back to a shell: a dead worker, as with Claude Code.

| Supervisor permission mode | Codex approval | Codex sandbox |
|---|---|---|
| `auto` | on-request, reviewed by Codex's auto review (`approvalsReviewer: auto_review`) | `workspace-write` |
| `acceptEdits`, default | on-request, the owner reviews | `workspace-write` |
| `dontAsk` | never asks | `workspace-write` |
| `bypassPermissions` | never asks | `danger-full-access` |

The workspace sandbox has network on (a worker pushes and opens PRs) and
these extra writable roots: the repo's git common dir, rollcall's store
(`~/.rollcall`), the task's files folder, `~/.cache`, and
`ROLLCALL_CODEX_ADD_DIRS` (colon-separated).

**The protocol stands in for Claude Code's hooks.** Each app-server event goes
through the same `workerHook` as the Claude Code hook of that name, so a
Codex worker's task record moves the same way:

| App-server event | Acts as |
|---|---|
| `item/started` (a user message) | prompt-submit |
| `turn/completed` | stop; on a failed turn stop-failure, and a `usageLimitExceeded` error starts the usage-limit wait with Codex's own reset time |
| approval server requests / `serverRequest/resolved` | the dialog flag up / down |
| `item/tool/requestUserInput` (Codex's question tool) | ask: the question goes to the owner's picker in the supervisor, and the tool gets the same "went to the owner's picker" answer Claude's deny carries |
| `thread/tokenUsage/updated` | context use and the handoff cap flag |
| `account/rateLimits/updated` | the usage meter |

What a hook would add to the model's context goes in as a steer into the
running turn; the cap's Stop block becomes a new turn. rollcall's own words
(the owner's `@tN` lines, picks, doorbells, notices) go in through the
protocol too (`rollcall _codex-send`, `src/codex/send.mjs`): `turn/start` when
the worker is idle, `turn/steer` into a running turn, and the server's answer
is the receipt. Nothing is typed, so the owner's half-written words in the UI
are never touched, and rollcall reads nothing off a Codex worker's screen.
rollcall's messages carry a `clientUserMessageId` that starts `rollcall-`, so
a prompt without one came from the owner typing in the UI and goes on the
record as their words. Interrupt is `turn/interrupt`.

Parking, resume, crash recovery and handoff work as for Claude Code: parking
relaunches the window with a resume script, and resume is `thread/resume` of
the recorded thread id. Codex reports no background work at a turn's end, so
a Codex worker counts as having nothing running once its turn ends.

**Hooks and guards.** rollcall adds no hooks of its own to a Codex worker. The
owner's own Codex hooks (projected into `~/.codex/hooks.json` by the bridge:
the PreToolUse guards, rollcall's main-checkout and shared-checkout denials)
run on its tool calls once trusted. At each start the worker reads
`hooks/list` and, when some are untrusted, puts a note on the task and news
for the supervisor, who tells the owner; the owner
trusts them once in the worker's window ("Review hooks", then trust all) or
with `/hooks`.

**Questions.** Outside plan mode Codex's question tool needs the
under-development flag `default_mode_request_user_input`; the worker's app
server starts with it on (`ROLLCALL_CODEX_QUESTIONS=0` turns it off). Where
the tool is not offered, the brief tells a Codex worker to ask with `rollcall
task set <id> --state needs-you --question "..."`.

**The brief.** `start.mjs` names the harness's own tools: a Codex worker hears
"your question tool (request_user_input)" where a Claude worker hears
AskUserQuestion, a note that it runs on Codex, and, since Codex has no
Artifact tool, to name before and after screenshots in its ship question
instead of publishing a page.

**The usage meter.** `~/.rollcall/usage-claude.json` and `usage-codex.json` (`src/usage.mjs`) hold how much
room each plan has. Claude's five-hour and weekly windows come from Claude
Code's status line JSON (`rate_limits`, on Pro and Max plans), recorded by any
session's `rollcall statusline`. Codex's come from `account/rateLimits/updated`
in a Codex worker, else from a short-lived `codex app-server`
(`account/rateLimits/read`), at most every ten minutes while a task runs on
Codex or Codex was read before. `rollcall usage` prints it (`Claude 5h 62% ·
wk 40% | Codex 5h 20%`), `task list` prints it as a `usage:` line, and the
supervisor's status line shows it dim, yellow once a plan is near: at or past
85% of a window (`ROLLCALL_USAGE_NEAR_PCT`). When one plan is near and the
other has room, the watcher sends the supervisor news ("usage-near") once per
task and window for each task on the full plan that waits (held by its limit,
not started yet, or parked or stopped while working). The supervisor asks the
owner whether to move it, and on yes runs `rollcall task move <id> --harness
<other>`. rollcall never moves a task by itself.

**Verification.** The Codex worker is tested end to end against a stand-in
Codex that speaks the app-server protocol
(`packages/rollcall/test/harness.test.mjs` with
`test/fixtures/fake-codex.mjs`; `test/codex-contract.test.mjs` checks the protocol
shapes against the installed Codex CLI and skips without one). The protocol shapes, and two clients on one
server (rollcall's `turn/start` showing live in the owner's UI), were checked
against the real Codex CLI 0.146.0-alpha.3. A full live task on Codex has not
run yet: the signed-in account was on a free plan with its monthly limit used
up until 2026-11-16.

**Owner steps.** Sign the Codex CLI in with your ChatGPT plan (`codex login`),
and trust the projected hooks once in Codex (`/hooks`, or "Review hooks" in a
worker's window).

### What Codex workers and a Codex supervisor still lack

- **A Codex supervisor.** The Falcon stays on Claude Code by the owner's
  decision. Codex has no custom status line command and no mods, so the chips
  and the band's task line would go, and its question tool is still under
  development, which the picker relay rests on. A later adapter can add it.
- **Mods and status line chips in a Codex worker's window.** Codex has no
  custom status line and no mods. The worker's tab in the Falcon still shows
  its state.
- **Telling a subagent's tool calls apart.** Codex marks none. rollcall
  follows only the worker's own thread (by thread id), and questions from a
  subagent's thread are not relayed to the owner.
- **Background work at a turn's end.** Codex reports none, so a Codex worker
  counts as having nothing running when its turn ends, even if it left
  something running.
- **The question tool** needs an under-development flag outside plan mode
  (above); a Codex release can change or drop it.
- **Gemini** is left out by the owner's decision: Gemini CLI stopped serving
  Google AI Pro/Ultra and free accounts on 2026-06-18.

## Delegation - running the agents on Codex

`kesselrunner delegate codex` makes the named agents (code-reviewer, test-runner,
test-updater, docs-updater, frontend-tester, deploy-watcher) run on the user's
Codex plan instead of as Claude subagents. Claude Code stays the orchestrator;
only the worker changes.

| Piece | Role |
|---|---|
| `lib/delegate.mjs` | The settings (written through `writeEnv`, which `kesselrunner rules` shares: `env.KESSELRUNNER_DELEGATE`, `env.KESSELRUNNER_CODEX_MODEL`, and `env.KESSELRUNNER_CODEX_EFFORT` in `~/.claude/settings.json`, so they are also available as shell environment variables), Codex CLI discovery (`KESSELRUNNER_CODEX_BIN`, `CODEX_CLI_PATH`, PATH, the ChatGPT app bundle, and `~/.codex/bin/codex`), login check, and model catalog |
| `lib/agents.mjs` | Shared agent frontmatter parsing and lossless TOML basic-string escaping used by the bridge and delegation runner |
| `scripts/delegate/run.mjs <agent>` | Runs one agent: `~/.claude/agents/<agent>.md` body -> Codex `developer_instructions`; task prompt (stdin / `--prompt-file`) -> user turn; `codex exec --ephemeral -C <cwd>` with hooks disabled (the worker must not re-run sync, the bridge, or docsic); prints only the final message + a trailer line; Codex's output streams live to a log in `$TMPDIR/kesselrunner-delegate/` (path on stderr at start and on the trailer) |
| `scripts/delegate/run.mjs status --hook` | SessionStart hook: one context line when the backend is codex (or why it cannot be used), silence otherwise |
| CLAUDE.md "Delegation" | Tells Claude what "spawn X" means on each backend. Skills and the deploy-watch hook say "spawn X" and never name the mechanism |

Exit codes of the runner: 0 done; 2 use the Agent tool (the backend is claude, or the
agent opted out with `codex: never`); 3 usage, unknown agent, or Codex unusable;
anything else is Codex's own exit code. Codex
status 2 is remapped to 1 because exit 2 is reserved for the Claude fallback.

Knobs (settings `env`, or agent frontmatter where noted):

| Knob | Default | Notes |
|---|---|---|
| `KESSELRUNNER_CODEX_SANDBOX` / frontmatter `codex_sandbox:` | `workspace-write` | Writes confined to the repo (`-C`), temp, and `--add-dir` roots: the repo's git common dir (worktrees keep it outside the checkout) plus existing build/cache dirs (Xcode DerivedData, CoreSimulator, XCTestDevices, `~/Library/Logs/CoreSimulator`, `~/Library/Caches`, `~/.npm`, `~/.cache`, pnpm/yarn/bun stores). Network on. `danger-full-access` lifts the sandbox; `read-only` forbids writes |
| `KESSELRUNNER_CODEX_ADD_DIRS` | none | More writable roots, colon-separated |

Verified with `codex sandbox` (no tokens): under `workspace-write` the extra roots make
DerivedData, `~/Library/Logs/CoreSimulator`, and the SwiftPM cache writable, but `xcrun simctl`
still fails - the seatbelt profile blocks the XPC connection to CoreSimulatorService. Simulator
suites therefore need `danger-full-access`; otherwise the worker reports them blocked and the
"Delegation" rule has Claude re-run exactly those on the Agent tool. An agent
whose whole job is the simulator (ios-driver) skips that round trip: frontmatter
`codex: never` makes the runner answer exit 2 before Codex starts, on every
sandbox setting.
| `KESSELRUNNER_CODEX_MODEL` / `codex_model:` | Codex `config.toml` model | Set with `kesselrunner delegate codex --model M` (validated against `codex debug models`; `kesselrunner delegate models` lists them). Frontmatter beats the global pick. The agent's `model: sonnet` line is Claude-only |
| `KESSELRUNNER_CODEX_EFFORT` / `codex_effort:` | the model's default effort | `--effort E`, validated against the model's supported efforts |
| `KESSELRUNNER_CODEX_BIN` | auto | Explicit CLI path |
| `KESSELRUNNER_DELEGATE_LOG_DIR` | `$TMPDIR/kesselrunner-delegate` | Where live logs and final messages land |

Verified mechanics (Codex CLI 0.146): `-c developer_instructions="""..."""` renders as a
developer-role message (`codex debug prompt-input` shows it); quotes,
backslashes, and control characters are escaped so arbitrary agent bodies
remain valid developer instructions. The global
`~/.codex/AGENTS.md` (the bridge's projection of CLAUDE.md) is loaded as usual, and
`--disable hooks` keeps the worker from running the SessionStart hooks.

GitHub CLI: `gh` stores its token in the macOS keychain, which the sandbox blocks (every `gh`
call 401s). Unless `GH_TOKEN`/`GITHUB_TOKEN` is already set, the runner resolves `gh auth token`
outside the sandbox and passes it to the worker as `GH_TOKEN` in the environment only (never on
the command line or in the log); Codex's shell environment policy passes it through.

What a Codex worker lacks vs a Claude subagent: Claude plugin MCP servers other than
Playwright (the bridge registers that one), and the `AskUserQuestion` tool (the
harness note tells the worker there is no user to ask).

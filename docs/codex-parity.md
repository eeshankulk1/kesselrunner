# Codex - Harness Parity and Agent Delegation

Two independent pieces connect kesselrunner to OpenAI Codex:

1. **The bridge** (below) makes a Codex session behave like a Claude Code session: same instructions, skills, agents, hooks.
2. **Delegation** (last section) lets a Claude Code session run its worker agents on the user's Codex plan.

## The bridge

kesselrunner is the single source of truth for the whole agent setup. The bridge
(`scripts/codex-bridge/generate.mjs`) projects `~/.claude` (as `kesselrunner sync` leaves it) into `~/.codex/` so OpenAI
Codex behaves identically to Claude Code. It runs as a SessionStart hook on
both harnesses and is idempotent: any change to kesselrunner propagates to Codex
on the next session start of either harness. It never overwrites Codex files it
did not generate (marker: `GENERATED by kesselrunner codex-bridge`).

## What maps 1:1 (automatic)

| kesselrunner source | Codex artifact | Mechanism |
|---|---|---|
| `~/.claude/CLAUDE.md` (core + switched-on optional rules + overlay block, plus the user's own text) | `~/.codex/AGENTS.md` | Generated copy + harness-mapping preamble. An optional rule (`kesselrunner rules on <name>`) sits in that block, so Codex sessions and delegated workers get it too |
| Per-repo `CLAUDE.md` | read directly | `project_doc_fallback_filenames = ["CLAUDE.md"]` in config.toml |
| `skills/*` | `~/.codex/skills/*` | Symlinks - SKILL.md is a cross-agent standard, zero translation |
| `agents/*.md` | `~/.codex/agents/*.toml` | Generated (name, description, body as `developer_instructions`) |
| `settings.json` `hooks` | `~/.codex/hooks.json` | Verbatim projection - Codex hooks use the same events, stdin JSON, and `hookSpecificOutput` contract as Claude Code |
| docsic hooks | unchanged | Codex documents the same `{session_id, cwd, transcript_path, prompt}` payloads; plain stdout from SessionStart/UserPromptSubmit hooks is injected as context on both harnesses |
| docsic distiller | unchanged | `docsic hook session-end` (once per rollcall task, at session end otherwise) auto-detects the CLI: `claude -p`, else `codex exec` (PATH, then the ChatGPT app bundle) |
| tool-call hook entries (`scripts/hooks/`) | unchanged (projected with the rest of `hooks`) | PreToolUse and PostToolUse each run one node process that calls the guards, deploy-watch and rollcall on the tools each matched alone, so the rows below hold as before |
| deploy-watch hook | unchanged | Codex documents `tool_input.command` as a string like Claude; the hook also tolerates argv-array `command` and bare-string `tool_response` defensively |
| rollcall hooks | unchanged (projected with the rest of `hooks`) | Same payload fields (`session_id`, `cwd`, `tool_name`, `tool_input`) and the same `hookSpecificOutput` deny/`additionalContext` contract on the events Codex fires. Harness pid detection walks process ancestry, so it is harness-agnostic; `status` tags Codex sessions `[codex]`. Codex's `apply_patch` edits are not matched (see Known gaps) |
| PreToolUse guards (core or overlay `hooks/pre-tool-use/`) | unchanged (projected with the rest of `hooks`) | Each guard reads `tool_input.command` as a string or an argv array and answers with the same `hookSpecificOutput` deny. Rules that key on Claude's tool names (`Read`, `Edit`, `Write`, `mcp__...`) apply only on Claude; on Codex a guard's shell rules hold. Delegated workers are not covered (see Known gaps) |

Verification status: the hook contract above is validated against the Codex
docs (v0.146) and by feeding both payload shapes to the scripts locally - not
yet against a live Codex session. First Codex session: confirm hooks fire
(memory injection appears) and spot-check `~/.codex/hooks.json` was trusted.

Hook commands point into the core checkout (absolute paths written by
`kesselrunner sync`), not at Claude Code, so they are valid even on a machine
that never runs Claude.

## One-time bootstrap on the Codex side

1. Run `node ~/.claude/kesselrunner/scripts/codex-bridge/generate.mjs` once (or just start
   a Claude session - the SessionStart hook does it).
2. In a Codex session, run `/hooks` and trust the generated hooks. Codex
   requires per-hash trust; re-approval is asked when a hook command changes.
3. Optional: put the CLI on PATH -
   `ln -s "/Applications/ChatGPT.app/Contents/Resources/codex" /usr/local/bin/codex`.

## Known gaps (no Codex equivalent, degrade gracefully)

- **PreToolUse guards in delegated workers**: `scripts/delegate/run.mjs`
  starts Codex with hooks disabled, so no guard (core or overlay
  `hooks/pre-tool-use/`) runs inside a delegated worker. Whatever limit a
  guard's tool has outside the harness (an API's own scopes, a tool's own
  rules) is what holds there.
- **Claude plugins** (`enabledPlugins`): supabase, vercel, context7,
  chrome-devtools etc. are Claude-plugin MCP servers. The bridge adds only
  Playwright MCP (hard dependency of frontend-tester) to `config.toml`;
  add others under `[mcp_servers.*]` manually if a workflow needs them.
- **Mods** (`mods/`: rollcall-band, pr-band, clickable): they draw inside
  Claude Code's terminal UI only. Codex sessions and delegated workers show no
  bands and load no mods; nothing the mods show is needed by an agent.
- **Supervisor mode** (`/supervisor`, `scripts/supervisor/start.mjs`): Claude
  Code only. Workers are interactive `claude` sessions in tmux with hooks from a
  launch settings file; the supervisor's news comes from a detached watcher
  process that types into its tmux pane and reads the turn records its hooks
  write (SessionStart, Stop, UserPromptSubmit); its chips are a status line
  command, and `@tN` routing and picks are UserPromptSubmit and PostToolUse
  hooks. Codex has none of these. The continued-in handover of a backgrounded
  supervisor reads Claude Code's transcript.
- **`/update-tests`** uses kesselrunner's own `test-updater` agent, so it works on
  Codex.
- **`AskUserQuestion`** in `make-tiktoks`: Codex has no structured-question
  tool; the model falls back to asking in plain text.
- **Claude auto-memory** (`MEMORY.md` behavioral preferences): Claude-only by
  design; durable project facts belong in docsic memory, which both harnesses share.
- **claude-code-guide agent**: Claude-only. For Codex harness questions,
  consult https://developers.openai.com/codex.
- **Model/effort settings** (`model`, `effortLevel`): harness-specific by
  nature; Codex keeps its own in `config.toml`.
- **rollcall on Codex** (unverified live): Codex hook coverage is contested
  (docs say the same events; one report says Bash-only PreToolUse and no
  lifecycle events), and Codex edits files through `apply_patch`, which the
  `Edit|Write|MultiEdit|NotebookEdit` matcher does not match. Expect Codex
  sessions to get session-start and prompt-time notices and the CLI, but no
  shared-checkout deny or overlap warning on their own edits (if Codex fires
  PreToolUse for its shell tool as `Bash`, the git guard still applies; the merge queue needs
  no hook at all: its lander is a script, and a Codex shipper hears its news from
  `rollcall queue wait`, the CLI, just without the `[rollcall] merge queue:` notice). Claude sessions
  still see Codex sessions as peers. `wait` needs a harness that wakes on a
  background command's exit; without one, run it in the foreground. Verify
  on the first live Codex session: `rollcall status` from Codex should list it.

## Safety properties

- `config.toml` is edited surgically (three keys, each skipped if present) and
  backed up once to `config.toml.bak-codex-bridge` before the first edit.
- `~/.codex` belongs to the ChatGPT desktop app's Codex; the bridge only adds
  to it and refuses to replace any file lacking its generation marker.
- Removing a skill/agent from kesselrunner removes its projection on next run;
  hand-written Codex skills and agents are never touched.

## Delegation - running the agents on Codex

`kesselrunner delegate codex` makes the named agents (code-reviewer, test-runner,
test-updater, docs-updater, frontend-tester, deploy-watcher) run on the user's
Codex plan instead of as Claude subagents. Claude Code stays the orchestrator;
only the worker changes.

| Piece | Role |
|---|---|
| `lib/delegate.mjs` | The settings (written through `writeEnv`, which `kesselrunner rules` shares: `env.KESSELRUNNER_DELEGATE`, `env.KESSELRUNNER_CODEX_MODEL`, and `env.KESSELRUNNER_CODEX_EFFORT` in `~/.claude/settings.json`, so they are also available as shell environment variables), Codex CLI discovery (`KESSELRUNNER_CODEX_BIN`, `CODEX_CLI_PATH`, PATH, the ChatGPT app bundle, and `~/.codex/bin/codex`), login check, and model catalog |
| `lib/agents.mjs` | Shared agent frontmatter parsing and lossless TOML basic-string escaping used by the bridge and delegation runner |
| `scripts/delegate/run.mjs <agent>` | Runs one agent: `~/.claude/agents/<agent>.md` body -> Codex `developer_instructions`; task prompt (stdin / `--prompt-file`) -> user turn; `codex exec --ephemeral -C <cwd>` with hooks disabled (the worker must not re-run sync, the bridge, or docsic); prints only the final message + a trailer line; Codex's output streams live to a log in `$TMPDIR/kesselrunner-delegate/` (path on stderr at start and on the trailer) |
| `scripts/delegate/run.mjs status --hook` | SessionStart hook: one context line when the backend is codex (or why it cannot be used), silence otherwise |
| CLAUDE.md "Delegation" | Tells Claude what "spawn X" means on each backend. Skills and the deploy-watch hook say "spawn X" and never name the mechanism |

Exit codes of the runner: 0 done; 2 use the Agent tool (the backend is claude, or the
agent opted out with `codex: never`); 3 usage, unknown agent, or Codex unusable;
anything else is Codex's own exit code. Codex
status 2 is remapped to 1 because exit 2 is reserved for the Claude fallback.

Knobs (settings `env`, or agent frontmatter where noted):

| Knob | Default | Notes |
|---|---|---|
| `KESSELRUNNER_CODEX_SANDBOX` / frontmatter `codex_sandbox:` | `workspace-write` | Writes confined to the repo (`-C`), temp, and `--add-dir` roots: the repo's git common dir (worktrees keep it outside the checkout) plus existing build/cache dirs (Xcode DerivedData, CoreSimulator, XCTestDevices, `~/Library/Logs/CoreSimulator`, `~/Library/Caches`, `~/.npm`, `~/.cache`, pnpm/yarn/bun stores). Network on. `danger-full-access` lifts the sandbox; `read-only` forbids writes |
| `KESSELRUNNER_CODEX_ADD_DIRS` | none | More writable roots, colon-separated |

Verified with `codex sandbox` (no tokens): under `workspace-write` the extra roots make
DerivedData, `~/Library/Logs/CoreSimulator`, and the SwiftPM cache writable, but `xcrun simctl`
still fails - the seatbelt profile blocks the XPC connection to CoreSimulatorService. Simulator
suites therefore need `danger-full-access`; otherwise the worker reports them blocked and the
"Delegation" rule has Claude re-run exactly those on the Agent tool. An agent
whose whole job is the simulator (ios-driver) skips that round trip: frontmatter
`codex: never` makes the runner answer exit 2 before Codex starts, on every
sandbox setting.
| `KESSELRUNNER_CODEX_MODEL` / `codex_model:` | Codex `config.toml` model | Set with `kesselrunner delegate codex --model M` (validated against `codex debug models`; `kesselrunner delegate models` lists them). Frontmatter beats the global pick. The agent's `model: sonnet` line is Claude-only |
| `KESSELRUNNER_CODEX_EFFORT` / `codex_effort:` | the model's default effort | `--effort E`, validated against the model's supported efforts |
| `KESSELRUNNER_CODEX_BIN` | auto | Explicit CLI path |
| `KESSELRUNNER_DELEGATE_LOG_DIR` | `$TMPDIR/kesselrunner-delegate` | Where live logs and final messages land |

Verified mechanics (Codex CLI 0.146): `-c developer_instructions="""..."""` renders as a
developer-role message (`codex debug prompt-input` shows it); quotes,
backslashes, and control characters are escaped so arbitrary agent bodies
remain valid developer instructions. The global
`~/.codex/AGENTS.md` (the bridge's projection of CLAUDE.md) is loaded as usual, and
`--disable hooks` keeps the worker from running the SessionStart hooks.

GitHub CLI: `gh` stores its token in the macOS keychain, which the sandbox blocks (every `gh`
call 401s). Unless `GH_TOKEN`/`GITHUB_TOKEN` is already set, the runner resolves `gh auth token`
outside the sandbox and passes it to the worker as `GH_TOKEN` in the environment only (never on
the command line or in the log); Codex's shell environment policy passes it through.

What a Codex worker lacks vs a Claude subagent: Claude plugin MCP servers other than
Playwright (the bridge registers that one), and the `AskUserQuestion` tool (the
harness note tells the worker there is no user to ask).

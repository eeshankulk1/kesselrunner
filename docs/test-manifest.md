# Test Manifest Convention

`.claude/test-manifest.json` at a project's repo root caches the facts test tooling otherwise re-discovers on every run: what stacks exist, exact test/build commands, dev server details, auth bypass, key routes. The test-runner agent, /frontend-test and /ios-sim read it first and skip discovery when it's present; whoever discovers a missing or wrong fact rewrites the file. It is committed to the project repo.

Trust-but-verify: entries are hints, not gospel. If a command from the manifest fails in a way that smells stale (script no longer exists, port moved), re-discover, use the corrected value, and update the file in the same session.

## Schema (all fields optional - include what the project actually has)

```json
{
  "updated": "2026-08-01",
  "stacks": [
    { "name": "web", "dir": ".", "runner": "vitest", "tier": "fast", "testCommand": "npx vitest run", "buildCommand": "npm run build" },
    { "name": "api", "dir": "backend", "runner": "pytest", "tier": "fast", "testCommand": ".venv/bin/pytest tests/ -x --tb=short -q", "envSetup": "source backend/.venv/bin/activate",
      "inputs": ["backend/**", "!backend/docs/**", ".github/workflows/ci.yml"], "check": "api*" },
    { "name": "ios-screenshots", "dir": ".", "runner": "xcuitest", "tier": "full", "ci": "nightly", "testCommand": "xcodebuild ... -only-testing:AppUITests/ScreenshotTests" }
  ],
  "ci": { "workflows": ".github/workflows/ci.yml (per PR), nightly.yml", "watch": "gh pr checks <pr> --watch --interval 30", "failedLogs": "gh run view <run-id> --log-failed", "notes": "...",
          "prePush": [{ "name": "ios", "when": ["ios/**"], "inputs": ["ios/**", "Makefile"], "command": "make ios-check", "ship": "make ios-check SHIP=1", "attest": "make ios-attest",
                       "flakes": "ios/UITests/run-alone.txt", "rerun": "ios/Scripts/ui-tests.sh demo --test <test>" }] },
  "ports": { "default": 3000 },
  "devServer": { "command": "npm run dev -- --port {port}", "port": "{port}", "baseUrl": "http://localhost:{port}" },
  "run": { "web": { "command": "npm run dev -- --port {port}", "port": "{port}", "url": "http://localhost:{port}" }, "api": { "command": "make dev-api PORT={port+1}", "dir": "backend", "url": "http://localhost:{port+1}" } },
  "backend": { "baseUrl": "http://localhost:8000", "startCommand": "make dev-api", "seedCommand": null, "resetCommand": null },
  "auth": { "bypassEnv": "E2E_TEST_AUTH", "notes": "dev-only, guarded on NODE_ENV" },
  "routes": { "key": ["/", "/dashboard"], "skip": ["/login"] },
  "ios": { "bundleId": "com.example.app", "buildCommand": "xcodebuild -project ios/App.xcodeproj -scheme App -destination 'platform=iOS Simulator,id=<UDID>' build", "generate": "cd ios && xcodegen generate",
           "fixtures": { "chat": { "args": ["--demo-chat"], "shows": "a seeded conversation, no account or backend" } },
           "signIn": "test user via the UI tests' helper (email + fixed code) against the local backend", "notes": "the menu is a drawer over the chat: both stay in the accessibility listing" },
  "worktree": { "setup": "scripts/worktree-setup.sh", "setupFlags": "--skip-ios when the task leaves ios/ alone", "teardown": "scripts/worktree-teardown.sh" },
  "land": { "serial": [{ "paths": ["backend/alembic/versions/**"], "why": "one migration head: chain yours after theirs" }] },
  "queue": { "guard": [{ "paths": ["backend/tests/fixtures/**"], "lines": ["@pytest\\.mark\\.flaky"] }] },
  "production": { "services": [{ "name": "api", "provider": "railway", "service": "app-api", "environment": "production" }, { "name": "web", "provider": "vercel", "project": "app-web" }],
                  "errors": { "provider": "sentry", "org": "acme", "project": "app-api" }, "database": { "readOnly": "psql \"$PROD_READONLY_URL\" (a read-only role; the URL lives in the user's env, never here)" }, "notes": "..." },
  "ship": { "model": "sonnet" },
  "release": { "merge": "merge", "afterMerge": [{ "name": "testflight", "when": ["ios/**"], "skill": "ship-build", "args": "post-merge" }], "production": { "words": ["prod", "production"], "skill": "prod", "notes": "A merge deploys staging only; a published GitHub Release deploys production." } },
  "notes": "anything non-obvious the next run should know (flaky suites, required docker services, ...)"
}
```

- `stacks[].testCommand` is the exact command that works from the repo root (or `dir`), venv paths and all - the point is zero rediscovery.
- `stacks[].tier` splits the build phase from the ship phase (global CLAUDE.md "Build phase vs ship phase"): `fast` stacks (unit, type-check, build; seconds to a couple of minutes) run after ordinary edits and again before every push; `full` stacks (simulator/browser UI suites, screenshot captures, anything needing a running stack and minutes of wall time) run only in the ship phase - in CI when `ci` says so, else locally from `/pr-create` - or when the user asks for the full suite. Untagged stacks default to `fast`, except runners `xcuitest`/`playwright` or names containing `UITests`/`e2e`/`screenshot`, which default to `full`.
- `stacks[].ci` says where CI runs the stack: `"pr"` (every PR that touches its paths), `"nightly"` (scheduled), or absent (nowhere - local only). Any `ci` value makes the stack CI's job: the ship phase never runs it locally. `/pr-create` watches the PR's checks for `"pr"` stacks, and for a `"nightly"` stack whose coverage the diff touches it dispatches just those suites (say how in `ci.notes`, e.g. a `workflow_dispatch` with a suite filter) and watches that run. Only stacks with no `ci` field run locally in the ship phase. The top-level `ci` block says how to watch and read CI (`watch`, `failedLogs`) and anything a watcher should know (self-hosted runners that can be offline, what a push to main re-runs). `/ci-setup` writes both; no `ci` anywhere means the project has no CI and the ship phase runs everything locally.
- `stacks[].inputs` (and `ci.prePush[].inputs`) are globs naming every file the check reads: its code, its tests, its fixtures, and what defines how it runs (the workflow file, the Makefile target). `rollcall results` keys a pass on them: the key is a hash of those files' contents at a commit, so a check whose inputs already passed on any commit is skipped - after a merge of main that touched other files, a docs amend, or in another ship's tree (`rollcall results check <name>`; CI runs the same file, see `/ci-setup`). `**` spans folders, `*` stays within one, `{a,b}` gives alternatives, a plain path names a file or a whole folder, and a leading `!` excludes. Absent: the whole repo for a stack, the entry's `when` globs for a pre-push entry - always safe, never skipped by accident. Narrow them on purpose and err wide: a file the check reads but its inputs leave out lets a pass stand for code it never ran on. The key covers files, not the command: list `.claude/test-manifest.json` too when a changed `testCommand` should run the check again.
- `ci.prePush` is the exception to "CI stacks never run locally": suites whose only CI home is a scarce runner (one self-hosted machine, one job at a time), where N open PRs wait on each other. Each entry runs on the shipper's own machine instead: `/pr-create` starts `command` in the background when a changed file matches `when` (beside the review, so it adds little wall time, and every shipper's machine runs its own), then runs `attest` after each push. An entry's optional `notes` say how to scope `command` to the diff (e.g. `"command": "make ios-check SUITES=\"<suites>\""` with notes on which suites cover which screens): keep the pre-push run to what the change touches and let the full suite run after the merge, gating the release rather than the PR. `attest` records the pass where the workflow's gate job looks (a commit status naming the tree that passed) and must refuse, with a documented exit code, when the pushed code is not the code that passed. An entry's optional `ship` splits the run between the ship and the merge queue's train, so each suite runs once per change: `/pr-create` runs `ship` instead of `command` (only the suites the diff names directly, without a widening to every suite, such as an iOS project's for a file every screen draws), and the suites `ship` leaves out run after the merge, in the default branch's own full run (with `land.retest`, the lander runs `command` on the train instead, which skips the suites that already passed with the same files and so runs only the rest; it does so even on a head that already holds the default branch, and without `ship` only on a tree nobody tested). After a `ship` run that left suites out, `attest` posts what the PR's gate accepts but does not record the entry's own key (`rollcall results record <name>`), or the train would skip the rest. The workflow keeps the runner as the fallback for commits nobody attested. The stacks an entry covers keep `ci: "pr"`: the check still lands on the PR, and test-runner still leaves them alone. Put the refusal exit code and the fallback behavior in `ci.notes`.
- `backend` powers ad-hoc feature validation (curling new endpoints): where the API runs, how to start it, how to get deterministic data (`seedCommand`) and back to clean (`resetCommand`). Leave commands null where the project has none - validation stays ad-hoc, just no longer blind.
- `auth` has two shapes. `bypassEnv`: an env var that stubs the session in dev (the app carries the bypass). `storageState` + `storageStateCommand` (e.g. `{ "storageState": "frontend/e2e/.auth/user.json", "storageStateCommand": "cd frontend && npm run e2e:auth" }`): a Playwright signed-in browser state (cookies + localStorage) that the command writes by signing a test user in for real - no bypass code in the app. /frontend-test regenerates the state when it's missing or older than its session lifetime, and the tester loads it before the first navigate.
- `worktree.setup` runs once in a fresh task worktree (global CLAUDE.md "Worktrees"): everything a new checkout needs before the fast tier passes - dependency installs, a per-worktree database branch, env files beyond what `.worktreeinclude` copies. For a task worktree rollcall runs it itself, in the background, before the worker's first turn: first the copy of the gitignored files `.worktreeinclude` names from the main checkout, then this command, with no stdin, a log and a 30-minute limit (`ROLLCALL_SETUP_MINUTES`). The worker's launch waits for it, and a failure goes on the task and to the supervisor once (`rollcall setup --rerun` runs it again). It gets the `ROLLCALL_*` environment below. `worktree.teardown` undoes whatever setup created outside the worktree (e.g. deletes that database branch); `rollcall gc` runs it from inside the worktree before removing it, and keeps the worktree if it fails. `worktree.setupFlags` is optional text: a supervisor's worker reads the setup command and these words in its brief, so it need not open the script to learn its flags. Both commands run from the worktree root; omit them when a plain checkout plus `npm ci` (or equivalent) is enough. For env files alone, a `.worktreeinclude` (gitignore syntax) at the repo root is enough: Claude Code copies them into worktrees it creates itself, and rollcall reads the same file for the task worktrees it makes. A worktree taken over with `--worktree` gets nothing new, and a discussion task gets the copy only.
- `{port}` and `{port+N}`: any string in the manifest may say them. `{port}` is the first port of this checkout's block, `{port+N}` the Nth after it. rollcall gives each checkout a block of 10 consecutive ports (41000-48999 by default; `ROLLCALL_PORT_MIN`, `_MAX`, `_BLOCK`), checked free when handed out and given back when gc removes the worktree or the task is archived. `task new` hands one out when the manifest uses `{port}`. Tasks in parallel then run their own servers without clashing. A project that does not use `{port}` behaves as before.
- `ports.default` is the port the main checkout uses for `{port}` (a worktree gets a block instead).
- `rollcall manifest [--json]` prints the manifest with this checkout's ports filled in. Test tooling reads ports and URLs through it, and falls back to the raw file where rollcall is absent.
- `run` names the actions that serve or exercise the checkout: `{ "<name>": { "command", "dir"?, "url"?, "port"? } }`. `rollcall run start|stop|restart <name|all>` starts each as its own process group with a log (under `_runtime/<key>/actions/` in rollcall's store); a `port` also reaches the command as `PORT`, and a running action's `url` is the task's preview link. Without `run`, `devServer.command` is an action named `dev` and `backend.startCommand` one named `backend`. `rollcall serving <port|url>` says which checkout serves a port (exit 0 this one, 1 another, 2 nothing): a browser or live-API check trusts a result only after exit 0.
- Environment for `worktree.setup`, `worktree.teardown`, run actions and the worker: `ROLLCALL_WORKTREE`, `ROLLCALL_MAIN_CHECKOUT`, `ROLLCALL_DEFAULT_BRANCH`, `ROLLCALL_PORT` (the block's first port), `ROLLCALL_PORT_COUNT`, `ROLLCALL_TASK_ID`, `ROLLCALL_TASK_HOME`, `ROLLCALL_TASK_NAME`.
- Hardcoded ports are the risk. Anything outside the manifest that names a fixed port breaks in a worktree on another one: OAuth redirect URIs, CORS allowlists, mobile app configs, docker-compose files. Search the repo for the old port number (`rg ':3000\b|3000'`) and move each hit to `{port}` or an env var. Where a service cannot move (a callback registered on one URL, an iOS bundle with a fixed host), `rollcall task spotlight <id>` runs that task's files from the main checkout instead.
- `land.retest: true` makes the merge queue test every PR merged with what landed before it, in trains, before it lands. Without it (the default since 2026-11-07), a PR green on its own head that merges cleanly lands as it is, in seconds, and the default branch's checks after the merge are the safety net: a project that sets nothing here should run its full suites on pushes to the default branch and hold its release while they are red. A `ship` split's leftover suites then run there, after the merge, not on a train.
- `land.serial` tells the merge queue (`rollcall queue`, joined by the ship script once a PR's checks are green: `rollcall ship start --land`) about changes that clash although git merges them. Each entry is a group of `paths` globs: two PRs that both change a path in the same group never share a train, and a PR whose group the default branch changed since it was cut goes through a train rather than landing as it is, so it is built and tested on top of what landed. `why` says what clashes (one migration head, prompt files and the recordings keyed on them); typical groups: a migrations directory with a single head, prompt files together with the recordings keyed on them, a generated lockfile or schema snapshot. Textual conflicts need no entry: the lander finds those itself and sends them back.
- `stacks[].check` names the CI checks a stack reports as (a string or a list; `*` matches any run of characters, so `"api*"` covers `api (sqlite)` and `api (postgres)`). The merge queue's lander uses it to blame a red train: the entries whose changed files fall in that stack's `inputs` are the suspects. One suspect goes back to its session; several are each tested alone; a failing check no stack claims suspects every entry in the train. Absent: every entry is a suspect, so a red train costs a round per entry instead of one.
- `ci.prePush[].flakes` and `rerun` let the merge queue's lander get past a known flaky test instead of sending a PR back for it. `flakes` names the project's list of known flakes, a file in the repo: one test per line, `#` starts a comment. `rerun` runs one test, `<test>` standing for its name (the lander fills it in, shell-quoted). When the lander runs `command`, `ROLLCALL_FAILURES` holds the path of an empty file, and the command writes every failure to it, one per line: a failed test, named as the list names it, and any other text for a failure that is not one test (a build error, a crash, a group with no result). When the command fails, every line names a test the default branch's list holds (so a PR cannot list its own failure) and both fields are set, the lander runs each of those tests once more with `rerun`. All pass: the suite counts as passed, its pass is recorded, `attest` runs with `ROLLCALL_FLAKES` set to the tests (space-separated), and each PR in the train gets a comment naming them, as does the landed line its session hears. Any other line, an empty file, or a test that fails again alone: the train is red as before. A command that does not write the file, or one the lander stopped (hung, or past its time limit), never takes this path; write a line for every way the command can fail, since a flake line beside an unwritten failure lets that failure land. A line in that file is a promise: the run will end red. Unless the line is a known flake, the lander stops the suite there, so write a failure only once it is final (after your own retry), never one a later retry may clear.
- `queue.guard` adds project patterns to the guard the merge queue runs when a PR joins again after it was sent back: `paths` globs (a change to one of these files parks the PR for the owner) and `lines` regexes (an added line that matches parks it). Built in, before any of these: removed test functions or assertions, added skips (`pytest.mark.skip`, `XCTSkip`, `.skip(`, `.only(`), edited `.github/workflows/**`, a changed `testCommand`, `command`, `ship`, `when`, `inputs`, `check`, `flakes` or `rerun` in this manifest, an edited known-flake list (`ci.prePush[].flakes`), and changed snapshot or reference-image files.
- `ship.model` names the model `/pr-create`'s shipper runs on (the part of a ship before the PR opens); absent means `opus`. It exists for the Sonnet shipper trial: set it per project, and a cheaper shipper that fails a step twice, or meets a logic fix no reviewer made, stops with `STEP UP` and an Opus shipper takes the ship over from where it stands. `rollcall usage report` puts each shipper model's ships side by side (quality, spend before the first push, step-ups), which is how the trial is judged.
- `release` drives the tail of the ship chain (rollcall's ship script, after `rollcall ship start --land`, which `/pr-create` runs when the user said "ship it"). `merge` is the merge method the lander passes to `gh pr merge` (`merge`, `squash` or `rebase`; absent: whatever the repo's recent PRs landed as). The merge queue reads it too: where PRs land as merge commits it lands up to 4 at a time as one train (one tree, one train PR); `squash` or `rebase` lands them one at a time. `afterMerge` lists what runs once the merge's deploys are watched: each entry runs when a changed file matches one of its `when` globs (no `when`: every merge), either a `skill` (invoked with `args`) or a `command` run from the repo root. The ship script runs each `command` itself, in a checkout of merged main (`worktree.setup` first), once what the merge started on GitHub is green; it stops at the first `skill` and hands that one and the rest to the task's worker, since a skill needs a model. Prefer a `command` where a script can do the step. Omit `release` when a merge is the whole release (auto-deploying web apps).
- `release.production` is for a project where a merge reaches staging and production is a separate, deliberate step. `words` are what the user says to run it ("prod"), `skill` (with optional `args`) or `command` is what runs, and `notes` say what a merge deploys and what production deploys, so a watcher judges the right environment (the same commit can carry a staging deployment from its merge and a production one from its release). With this entry, "ship it" ends on staging: `/pr-create` watches the staging deploy, runs `afterMerge`, and reports that production is unchanged and which word releases it. It never runs the production entry itself. `publish: "owner"` is an opt-in for a project whose production release the owner publishes by hand: the entry prepares the release, hands the owner the command that publishes it, and takes over again once the release exists. A PreToolUse guard (core or overlay `hooks/pre-tool-use/`) can read this field to deny an agent the publish in that project only. Without `publish`, the agent publishes, as the entry says. Without `release.production`, a merge is a production deploy, as before.
- `routes.key` seeds /frontend-test's shared-change blast radius (layout/global CSS -> test these); `routes.skip` is never auto-tested.
- `ios` is what /ios-sim needs to brief the ios-driver agent without rediscovery: the app's `bundleId`; `buildCommand`, the exact simulator build with `<UDID>` where the device goes; `generate` when the Xcode project is generated; `fixtures`, the launch arguments (or `env`) that render a screen with seeded data and no account or backend, each with what it `shows` - the cheapest state to check a screen in; `signIn`, how a test user gets in when a flow needs a real session; and `notes`, driving quirks the next run should know (views that stay in the accessibility listing under another, controls with no id, waits a screen needs). /ios-sim reads it first and writes back what a run learned.
- `production` is what /prod-read and the prod-reader agent need to read the live system without rediscovery, and what `scripts/prod-read/read.mjs` reads. `services[]`: a `name`, a `provider` (`railway`: `service`, defaulting to the name, and `environment`, defaulting to `production`; `vercel`: `project`; `command`: the project's own read-only `status`, `logs` and `vars` commands, `vars` printing names first on each line; the script runs these through the shell as written, so review a change to them as you would code), and an optional `dir` under the main checkout where that service's CLI is linked. The script runs each CLI from the main checkout, since a task worktree has no provider link. `errors` names the error tracker's `provider`, `org` and `project`; `database.readOnly` says how to reach the database with a read-only role, never with a password written here; `notes` holds what a reader should know (which environment is which, noisy log lines to ignore). /prod-read drafts the block when it is missing.
- Supersedes the old `.claude/frontend-test.json`; if one exists, fold its values in here and delete it.

## Who writes it

Any agent or skill that had to discover one of these facts the hard way. Creating it is cheap (one write at the end of a discovery pass); keeping it honest is the `updated` field plus trust-but-verify above.

## Ownership vs docs (see also docs/project-docs.md)

The manifest is the **single home for command-grade facts**: exact test/build/dev-server commands, ports, seed/reset, auth bypass, key routes, the iOS app's simulator build and fixtures. Do not mirror them into docs:

- `docs/local-dev.md` keeps the narrative (prereqs, clone-to-running setup, env var meanings, seeded data, gotchas) and points at the manifest for exact invocations instead of duplicating flags and venv paths.
- Repo `CLAUDE.md` holds no commands at all - move any it has into the manifest and leave a pointer.
- On conflict, the manifest wins for command-grade facts (it is the copy agents actually heal); docs win for narrative and warnings. Fix the losing copy in the same session.
- **Exception - safety warnings**: destructive-command prohibitions (e.g. "never `supabase db reset` in this repo") are deliberately duplicated in the manifest `notes` AND local-dev.md AND any skill that could run the command.
